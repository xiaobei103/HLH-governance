# Testing_Standard.md：HLH AI 软件工程测试标准

> 本文件定义 HLH AI Software Engineering Workflow v3.2 的测试标准。
>
> **所有正式项目必须建立可执行、可记录、可复盘的测试流程。**
>
> **未测试不得说成通过。Build / Test 失败不得交付。**
>
> **Claude Code 不得通过删除测试、删除功能或降低标准来让测试"通过"。**

---

## 1. 文档定位

本文件是 `01-Standards/` 下的测试标准。

### 本文件回答的问题

- 什么任务必须测试？什么项目必须有测试命令？
- Build、Typecheck、Lint、Test 的区别和各自职责是什么？
- 单元测试、API 测试、E2E 测试、回归测试分别什么时候写？
- 数据库相关功能如何测试？AI/Agent 输出如何测试？
- 测试失败后 Claude Code 可以自动修复几轮？
- 没有测试命令时如何处理？
- 交付前必须输出哪些测试结果？

### 本文件不负责

- 具体测试代码实现 → `Coding_Workflow.md`
- 具体业务测试数据 → `Project_Workflow.md`

- 具体部署验收 → `Delivery_Standard.md`
- 数据库测试细节 → `Database_Standard.md`

## 2. 测试总原则

### 2.1 测试是交付底线，不是装饰品

测试不是"有时间就做"的加分项，而是"能否交付"的硬性标准。没有测试验证的代码不能声称"完成了"。

### 2.2 Build 成功不等于功能正确

Build 只验证代码能编译，不验证业务逻辑正确。Build 通过是最低门槛，不是测试终点。

### 2.3 没有测试必须明确标记风险

如果项目没有测试命令——这在 MVP 阶段可以接受——但必须在交付报告中明确标记 ⚠️，不能假装测试过了。

### 2.4 核心业务流程必须验收

无论项目处于什么阶段，核心业务流程（最关键的 1-2 个用户路径）必须经过人工或自动验收。没有验收 = 不知道能不能用。

### 2.5 测试失败不得交付

Build 红、Test 红、Typecheck 红——任一项不通过都不能说"做完了"。必须先修复，再交付。

### 2.6 不允许删除测试来让测试通过

删除一个失败的测试 ≠ 修复了一个 Bug。如果测试不合理，可以讨论修改测试，但不能直接删除。

### 2.7 不允许删除功能来让 Build 通过

删除报错的代码而不理解为什么报错 = 掩盖问题。理解原因后再决定是修复还是删除。

### 2.8 自动修复必须限制轮次

Build 或 Test 失败后，Claude Code 最多自动修复 3 轮。超过 3 轮必须停止并请求人工判断。

### 2.9 测试结果必须写入交付报告

执行了什么测试、结果如何、哪些没执行、为什么——全部记录。

### 2.10 测试标准必须匹配项目阶段，不搞形式主义

Prototype 阶段不要求 90% 测试覆盖率。Release 阶段不能只有 0%。测试要求随项目阶段逐步提升。

## 3. 测试风险等级

### T0：低风险

**示例：** 文档修改、README 修改、Workflow/Standards 修改、注释修改、不影响运行的文件修改

**规则：** 通常不需要 Build/Test，但必须说明"不适用"的原因。必须有 Git commit 和交付报告。

### T1：中风险

**示例：** 小范围前端 UI 修改、非核心组件修改、普通 API 修改、新增简单工具函数、非核心配置修改

**规则：** 必须尝试 Build。有 test 命令则必须运行。至少做相关功能手动验收。失败必须说明。

### T2：高风险

**示例：** 核心业务流程修改、数据库 schema 变更、登录/权限修改、数据导入导出修改、API 兼容性变更、架构调整、新增依赖、Agent 工具调用变更

**规则：** 必须 Build。必须运行相关 Test。必须进行回归测试。必须说明风险和回滚方案。失败不得交付。

### T3：禁止跳过测试

**示例：** 生产部署前、商业交付前、数据库 migration 前后、登录/权限上线前、支付/上传/导出功能上线前、客户数据处理上线前、Agent 执行高风险操作前

**规则：** 不允许以"应该没问题"或"时间不够"跳过。必须人工确认测试结果。必须写入交付报告。

## 4. 测试分层模型

### 4.1 Build Check

**目标：** 验证项目是否能正常构建。

```bash
npm run build    # 或 pnpm build
```

**作用：** 检查打包错误、基础编译问题、明显依赖缺失。**限制：** Build 通过不代表业务逻辑正确、API 正常或页面可用。

### 4.2 Typecheck

**目标：** 验证 TypeScript 类型是否正确。

```bash
npm run typecheck    # 或 pnpm typecheck / tsc --noEmit
```

**作用：** 检查类型错误、接口变化、未定义变量引用。

### 4.3 Lint

**目标：** 检查代码风格和明显质量问题。

```bash
npm run lint    # 或 pnpm lint
```

**作用：** 检查未使用变量、明显代码问题、保持代码一致性。**限制：** Lint 通过不代表功能正确。Lint 不等于测试。

### 4.4 Unit Test（单元测试）

**目标：** 测试单个函数、模块、服务的逻辑正确性。

**推荐工具：** Vitest、Jest

**适用：** 工具函数、业务规则、数据转换、校验逻辑、Agent 输出解析

### 4.5 API Test（接口测试）

**目标：** 测试后端接口的请求/响应是否符合预期。

**适用：** CRUD 接口、登录接口、查询接口、导入导出接口、权限接口、Agent 调用接口

### 4.6 E2E Test（端到端测试）

**目标：** 模拟用户真实操作流程，验证整个系统协作是否正常。

**推荐工具：** Playwright

**适用：** 登录流程、客户管理流程、数据录入流程、搜索筛选流程、表单提交流程、核心业务闭环

### 4.7 Regression Test（回归测试）

**目标：** 确认旧功能没有被新修改破坏。

**适用：** Bug 修复后、需求迭代后、重构后、数据库变更后、依赖升级后、Agent 流程修改后

### 4.8 Manual Acceptance Test（手动验收）

**目标：** 人工确认关键业务结果是否符合预期。

**适用：** 暂无自动测试的项目、MVP、接单项目、UI/交互验收、客户交付前检查

### 4.9 Agent / AI Output Test（AI 输出测试）

**目标：** 验证 AI/Agent 在固定输入下是否输出可接受结果。

**适用：** Prompt、Workflow、Skills、MCP 工具调用、Subagent 输出、AI 分析结果

## 6. 技术栈对应测试工具

| 技术栈 | 推荐测试工具 | 测试重点 |

| React + TypeScript + Vite | Vitest + Playwright | 组件渲染、表单校验、状态变化、页面流程 |

## 7. Build 标准

1. **如果 `package.json` 存在 `build` 命令，必须运行。**
2. **如果项目没有 build 命令，必须说明原因。**
3. **Build 失败不得交付。** 必须先修复，再交付。
4. **Build 失败必须分析原因。** 定位到具体文件和错误。
5. **不得通过删除功能让 Build 通过。** 删除代码而不理解原因 = 掩盖问题。
6. **不得通过注释掉关键代码让 Build 通过。** `// TODO: fix later` 不是修复。
7. **Build 输出摘要必须写入交付报告。**
8. **文档类任务可标记 Build 为"不适用"。**
9. **依赖变更后必须 Build。**
10. **数据库 schema 变更后必须 Build 或说明原因。**

---

## 8. Typecheck 标准

1. **长期项目应配置 `typecheck` 命令。** MVP 可先不做。
2. **类型错误不得忽略。** `// @ts-ignore` 不能成为常规操作。
3. **不得大量使用 `any` 掩盖类型问题。**
4. **API 类型变化必须同步前后端。**
5. **Prisma 类型重新生成后必须验证。**
6. **类型检查失败不得交付。**
7. **如果没有 typecheck 命令，必须在交付报告中说明。**
8. **求职作品集项目应体现 TypeScript 类型意识。**

---

## 9. Lint 标准

1. **长期项目应配置 lint。**
2. **Lint 失败必须说明原因。** 是本次修改引入的，还是已有问题。
3. **不得为了通过 lint 删除有效代码。**
4. **不得无关格式化整个项目。** 格式修改独立 commit。
5. **不得把格式化和功能修改混在一个 commit。**
6. **如果 lint 规则过严，可提出调整方案并等待确认，不得擅自修改配置。**
7. **文档类任务通常不需要 lint。**
8. **Lint 结果必须写入交付报告。**

---

## 10. Unit Test 标准

### 适合写单元测试的内容

- 工具函数（日期格式化、金额计算、数据转换）
- 权限判断函数
- 输入校验函数
- 搜索匹配逻辑
- Agent 输出解析逻辑

### 规则

1. **复杂逻辑应优先写单元测试。** 逻辑越复杂，越需要测试保护。
2. **Bug 修复应尽量补充复现测试。** 防止同一个 Bug 修复两次。
3. **单元测试不得依赖真实数据库。** Mock 或使用内存数据库。
4. **单元测试不得依赖真实外部 API。** Mock 或 stub。
5. **单元测试不得依赖真实密钥。** 使用测试占位值。
6. **测试数据应脱敏或虚构。**
7. **测试失败不得通过删除测试解决。**
8. **测试结果必须写入交付报告。**

## 11. API Test 标准

### API 测试应覆盖

| 场景 | 测试内容 |
|------|----------|
| 成功请求 | 正常参数、正常返回 |
| 参数缺失 | 必填字段为空时的错误响应 |
| 参数类型错误 | 字符串传入数字字段等 |
| 权限不足 | 无 Token、Token 过期、权限不够 |
| 数据不存在 | 查询不存在的 ID |
| 重复提交 | 唯一约束冲突 |
| 边界值 | 最大长度、最小值、空数组 |
| 错误处理 | 各异常分支的返回格式 |

### 规则

1. **API 修改后必须考虑 API 测试。** 改了接口就要验证接口。
2. **API 返回格式变化必须说明影响。** 前端哪些页面会受影响。
3. **API 错误不应泄露内部堆栈或数据库信息。**
4. **API 测试不得使用生产数据库。**
5. **API 测试不得使用真实客户数据。**
6. **权限相关 API 必须高优先级测试。**
7. **导入导出 API 必须测试异常数据。**
8. **API 测试失败不得交付。**

## 12. E2E Test 标准

### 推荐工具：Playwright

### 适合 E2E 覆盖的流程

登录 → 新增客户 → 编辑客户 → 搜索客户 → 删除/归档 → 导入导出 → 表单提交 → 数据看板 → Agent 操作流程

### 规则

1. **核心业务流程应逐步建立 E2E。** 从最重要的 1-2 条流程开始。
2. **E2E 使用测试账号和测试数据。** 永远不用真实用户账号。
3. **E2E 不得连接生产环境。**
4. **E2E 不得自动执行支付、交易、真实发送消息。** 这些是 P3 操作。
5. **E2E 失败必须分析原因。** 是代码 Bug 还是测试脚本问题。
6. **Playwright 可用于页面检查，但不得越权操作外部账号。**
7. **商业交付前至少应有手动 E2E 验收流程。**
8. **E2E 结果必须写入交付报告。**

## 13. Regression Test 标准

回归测试确认"改了 A，B 还好吗"。

### 必须回归的场景

Bug 修复、搜索逻辑修改、数据库 schema 修改、API 返回格式修改、权限逻辑修改、导入导出修改、前端核心页面修改、依赖升级、重构、构建配置修改

### 回归测试必须回答

| # | 问题 |
|---|------|
| 1 | 原问题是否已解决？ |
| 2 | 相关旧功能是否仍可用？ |
| 3 | 是否引入了新的错误或异常？ |
| 4 | 是否影响已有数据？ |
| 5 | 是否影响核心用户流程？ |
| 6 | 是否影响 Build / Test？ |
| 7 | 是否需要更新文档？ |
| 8 | 是否有未覆盖风险？ |

## 14. Database Test 标准

数据库测试必须遵守 `Database_Standard.md`。

### 测试内容

Schema 正确性、Migration 可执行性、Seed 可用性、查询正确性、数据约束生效、导入正确性、导出正确性、备份方案可用性、回滚可行性、测试数据库隔离性

### 规则

1. **数据库测试不得连接生产库。**
2. **数据库测试不得使用真实客户数据。**
3. **Migration 测试必须确认当前连接的数据库环境。**
4. **Seed 测试必须确认目标环境。**
5. **导入导出测试必须使用脱敏数据。**
6. **SQLite 数据文件不得在测试中误删。**
7. **数据库测试结果必须写入交付报告。**

## 15. Security Test 标准

安全测试应覆盖以下维度：

| 维度 | 检查内容 |
|------|----------|
| 输入校验 | SQL 注入、XSS、命令注入 |
| 权限访问 | 未授权访问、越权访问 |
| API 敏感字段 | 是否返回密码、Token、内部信息 |
| 密钥泄露 | `.env` 是否进入 Git、日志中是否有 Key |
| 文件上传 | 非法文件类型、超大文件 |
| 客户数据暴露 | API 响应、日志、前端 bundle |
| 依赖风险 | 已知 CVE、来源不明包 |
| 外部服务权限 | MCP 是否越权、Agent 是否越界 |

### 规则

1. **安全相关修改必须做安全检查。**
2. **登录/权限修改必须测试越权场景。**
3. **API 修改必须检查敏感字段是否泄露。**
4. **文件上传必须测试非法文件拦截。**
5. **导入导出必须测试权限和敏感字段过滤。**
6. **交付前必须执行安全检查清单。**
7. **安全风险必须写入交付报告。**

## 16. Agent / AI Output Test 标准

AI/Agent 的测试不同于确定性代码测试——输出可能每次不同，但边界应该稳定。

### 测试内容

| # | 测试项 | 验证什么 |
|---|--------|----------|
| 1 | 固定输入下输出是否在可接受范围 | 不是每次完全一样，但不能胡说 |
| 2 | 输出是否符合预期格式 | JSON 是合法 JSON，文本不包含乱码 |
| 3 | 输出是否包含不该包含的信息 | 没有密钥、没有客户数据、没有内部路径 |
| 4 | 是否调用了允许的工具 | 在工具白名单内 |
| 5 | 是否调用了禁止的工具 | 不在黑名单内 |
| 6 | 是否读取了无关文件 | 不跨项目、不读私人文件 |
| 7 | 是否访问了外部账号 | 不自动登录、不自动发消息 |
| 8 | 失败时是否停止 | 不无限重试、不乱猜 |
| 9 | 是否要求人工确认 | 高风险节点是否停下 |
| 10 | 是否写入日志或报告 | 行为可追溯 |

### 测试输入应包括

正常输入、空输入、模糊输入、恶意输入（Prompt 注入尝试）、超长输入、缺失上下文、工具调用失败、权限不足

### 规则

- Agent 不得为了完成任务绕过权限。
- Agent 不得自动连接外部账号。
- Agent 不得自动发送消息、支付、交易。
- Agent 输出**不得直接覆盖关键业务数据**——写入前需校验或人工确认。
- Agent 测试结果必须可记录、可复盘。

## 17. Manual Acceptance Test 标准

没有自动测试时，手动验收是最后的底线。

### 手动验收必须包含

| # | 步骤 |
|---|------|
| 1 | 启动项目（一条命令能启动） |
| 2 | 打开核心页面 |
| 3 | 执行核心业务流程 |
| 4 | 输入正常数据，确认结果正确 |
| 5 | 输入异常数据，确认有合理错误提示 |
| 6 | 检查数据是否已正确保存 |
| 7 | 刷新页面，确认数据仍在 |
| 8 | 检查控制台是否有异常错误 |
| 9 | 检查后端是否有异常日志 |
| 10 | 记录验收结果：通过 / 失败 / 部分通过 |

### 规则

- **"看起来没问题"不是验收。** 必须列出实际操作步骤和对应结果。
- **必须写明通过或失败。** 不能含糊。
- **手动验收结果必须写入交付报告。**
- **商业交付前必须逐项手动验收核心流程。**

## 18. Smoke Test 标准

Smoke Test 是快速冒烟测试——30 秒内判断系统是否"基本活着"。

### 适用场景

每次大修改后、Build 成功后、部署前、交付前、修复严重 Bug 后

### Smoke Test 内容

| # | 检查项 | 判断 |
|---|--------|------|
| 1 | 项目能启动 | 不会白屏或 crash |
| 2 | 首页能打开 | 不 404、不报错 |
| 3 | API 能响应 | 一个简单请求能返回 |
| 4 | 数据库能连接 | 启动日志无连接错误 |
| 5 | 核心页面能访问 | 不会卡在 loading |
| 6 | 核心按钮能点击 | 不报错、有反应 |
| 7 | 无明显控制台错误 | 红色报错 = 不通过 |
| 8 | 无明显后端错误 | 500 错误 = 不通过 |
| 9 | 环境变量缺失时提示合理 | 不静默崩溃 |
| 10 | 不出现白屏 | 白屏 = 不通过 |

### 规则

- **Smoke Test 不是完整测试。** 通过 Smoke Test ≠ 功能正确。
- **Smoke Test 失败不得继续交付。**
- **Smoke Test 成功后仍需执行相关功能测试。**

---

## 19. 测试失败处理规则

```
读取错误信息
    ↓
定位原因（哪个文件、哪个测试、什么错误）
    ↓
判断是否属于本次修改引起
    ↓
提出修复方案（最小范围修复）
    ↓
修改代码（不删除测试、不删除功能）
    ↓
重新 Build / Test
    ↓
记录结果
```

### 规则

1. **不允许忽略失败。** 红了就是红了，不能假装没看到。
2. **不允许把失败说成通过。** "基本通过"、"大概没问题" = 欺诈。
3. **不允许删除测试。** 测试失败修代码，不是删测试。
4. **不允许删除功能。** 功能报错修功能，不是删功能。
5. **不允许无关重构。** 修 Bug 就是修 Bug，不趁机重写。
6. **不允许无限自动修复。** 最多 3 轮。
7. **自动修复最多 3 轮。** 超限停止并询问用户。
8. **3 轮失败后必须停止并询问用户。** 说明原始错误 + 每轮尝试了什么 + 为什么还是失败。
9. **涉及数据库、安全、权限、部署时必须特别谨慎。** 这些领域的修复不能自动无限重试。
10. **失败原因和修复过程必须写入交付报告。**

---

## 20. 没有测试命令时的处理

如果项目没有测试命令，Claude Code 必须：

1. **明确声明没有发现测试命令。**
2. **说明 Build 是否存在以及是否已执行。**
3. **说明可以执行哪些手动验收步骤。**
4. **说明测试缺失带来的风险。**
5. **不得说"测试通过"。** 没测过就是没测过。
6. **在交付报告中写：⚠️ Test 未执行，原因：项目暂无 test 命令。**
7. **对长期项目，建议补充 test 命令。**
8. **对 MVP 项目，建议至少补充核心手动验收清单。**
9. **对商业项目，建议建立交付前验收流程。**
10. **不得为了省事跳过以上任何一步。**

## 21. 测试数据标准

测试数据必须安全、可控、可重复。

### 允许

- ✅ 虚构数据（张三、李四、test@example.com）
- ✅ 脱敏数据（已去除真实个人信息的数据）
- ✅ 测试专用账号
- ✅ 测试专用数据库
- ✅ 小规模样例数据

### 禁止

- ❌ 真实客户数据
- ❌ 真实手机号、微信号、邮箱
- ❌ 真实医疗信息、财务信息
- ❌ 真实成交记录、支付信息
- ❌ 真实账号密码
- ❌ 真实数据库备份

### 规则

1. **测试数据不得进入生产环境。**
2. **测试数据不得污染真实数据。**
3. **测试数据应容易重置。** 一个命令就能恢复干净状态。
4. **测试数据应覆盖正常和异常情况。**
5. **测试数据（seed、fixture）可进入 Git；真实数据永远不进 Git。**

## 22. Claude Code 测试权限

### 默认允许（P0–P1）

- 读取 `package.json` 中已有测试命令
- 运行已有 `build` / `test` / `lint` / `typecheck` 命令
- 阅读测试文件
- 修改当前任务明确指定的测试文件
- 输出测试结果到交付报告
- 分析测试失败原因并提出修复方案

### 必须确认后才能（P2）

- 新增测试依赖（`vitest`、`playwright` 等）
- 修改测试框架配置
- 修改 Playwright 配置
- 修改数据库测试配置
- 修改 CI 测试配置
- 删除测试文件
- 大规模重写测试

### 禁止自动（P3）

- 删除测试来让测试通过
- 降低测试标准来让任务完成
- 连接生产数据库执行测试
- 使用真实客户数据测试
- 自动执行支付、交易、真实发送消息的测试
- 因测试失败清空数据库
- 因测试失败删除功能代码

## 23. 测试与 Git 的关系

1. **测试代码应进入 Git。** 测试是源码的一部分。
2. **测试数据（seed、fixture）如果脱敏且必要，可以进入 Git。**
3. **真实测试输出、截图、视频默认不进入 Git，除非明确需要作为文档。**
4. **Playwright 截图和报告可按需忽略：**

```gitignore
test-results/
playwright-report/
coverage/
```

5. **测试失败修复应独立 commit。** `test: fix failing customer search test`
6. **依赖测试变化的功能 commit 必须说明。**
7. **Release 前测试结果应记录在 CHANGELOG 或交付报告中。**
8. **交付报告必须包含测试结果。**

## 26. 常见错误与处理

### 26.1 Build 失败

1. 阅读错误信息。
2. 判断是否由本次修改引起。
3. 最小范围修复。
4. 重新 Build。
5. 最多自动修复 3 轮。
6. 超限后停止并询问用户。

### 26.2 Test 失败

1. **不删除测试。**
2. 判断测试是否合理（测试本身有 Bug 还是代码有 Bug）。
3. 判断代码是否破坏了旧逻辑。
4. 修复代码，或提出测试更新方案并等待确认。
5. 重新运行测试。
6. 记录失败原因和修复过程。

### 26.3 没有测试命令

1. 明确说明缺失。
2. 执行可用的 Build。
3. 执行手动验收。
4. 在交付报告中标记 ⚠️ 风险。
5. 建议后续补充测试。

### 26.4 E2E 不稳定（时过时不过）

1. 分析是否等待条件不足（页面加载、API 响应）。
2. 分析是否测试数据不稳定（每次跑的测试数据不同）。
3. 分析是否依赖外部服务。
4. **不直接删除 E2E 测试。**
5. 调整等待策略或测试隔离。
6. 记录不稳定原因到交付报告。

### 26.5 Agent 输出不稳定

1. 固定输入条件。
2. 固定期望的输出格式。
3. 增加边界条件测试。
4. 限制 Agent 的工具权限。
5. 确保失败时 Agent 会停止而不是胡乱继续。
6. 记录失败样例到 Agent 测试日志。

## 28. 禁止事项

| # | 禁止事项 | 原因 |
|---|----------|------|
| 1 | 禁止未测试就说通过 | 没测过就是没测过 |
| 2 | 禁止 Build 失败还交付 | 编译不过的代码不能运行 |
| 3 | 禁止 Test 失败还交付 | 测试红了说明有 Bug |
| 4 | 禁止删除测试来让测试通过 | 删除测试 ≠ 修复 Bug |
| 5 | 禁止删除功能来让 Build 通过 | 不理解就删 = 掩盖问题 |
| 6 | 禁止降低测试标准来完成任务 | 把覆盖率从 80% 改成 50% ≠ 进步 |
| 7 | 禁止测试连接生产数据库 | 测试可能破坏生产数据 |
| 8 | 禁止用真实客户数据测试 | 客户数据安全不可妥协 |
| 9 | 禁止自动支付、交易、真实发消息测试 | P3 操作 |
| 10 | 禁止无限自动修复 | 最多 3 轮 |
| 11 | 禁止把 Smoke Test 当完整测试 | Smoke Test 只证明系统"活着" |
| 12 | 禁止没有交付报告就结束 | 测试结果必须在报告中 |
| 13 | 禁止隐藏未覆盖风险 | 不知道的风险 > 已知的风险 |
| 14 | 禁止把"看起来没问题"当验收 | 验收需要具体步骤和结论 |
| 15 | 禁止为了赶进度跳过核心流程测试 | 核心流程坏了 = 系统不能用 |

## 29. 当前阶段默认结论

1. **当前阶段文档类任务可不执行 Build/Test，但必须说明不适用。**
2. **未来代码类任务必须优先执行 Build。** Build 是最低门槛。
3. **长期项目必须逐步补齐 Typecheck → Lint → Unit Test → E2E。** 从 Build 开始，一层层加上去。
4. **MVP 至少必须有核心手动验收。** 不要求自动化测试，但必须有人确认过能用。
5. **商业交付前必须有完整验收清单。** 每一项通过后才能交付。
6. **数据库测试不得连接生产环境。** 必须使用独立的测试数据库。
7. **Agent 测试必须验证边界和失败停止机制。** Agent 不能无边界运行。
8. **自动修复最多 3 轮。** 超限停止，不无限重试。
9. **测试结果必须写入交付报告。** 没测写"没测"，测了写"通过/失败"，不能模糊。
10. **Testing Standard 必须先于正式产品开发完成。** 没有测试标准的项目不开工。

## 30. v3.2 运行验证证据边界

### 30.1 按场景触发持久化证据

Persistent Evidence Bundle 不作为所有 Work Package 或测试任务的默认要求。仅在运行时、外部边界、难以事后复核或治理要求触发时要求生成；普通文档修改、小范围静态调整或可直接复核的低复杂度验证，按本标准记录测试是否适用及结果即可。

当测试或验证涉及 Browser E2E、Provider、数据库、Hook、外部网络、环境依赖，或其他难以事后复现的运行时边界时，应按风险要求生成可独立复核的 Evidence Bundle，并保留原始命令、输出、环境、时间、关键状态和失败历史。

### 30.2 Agent Runtime 配置引用

Requested/Actual Model、Reasoning、Capability 等 Agent Runtime Evidence 由 `Agent_Collaboration_Standard.md` 定义。本标准仅在运行时配置可能影响测试或验证结论时引用并记录实际配置；不在此文件重新定义 Agent 治理字段，也不将具体模型绑定到测试角色。

### 30.3 验证状态

测试报告应区分 `PASS`、`PASS WITH OBSERVATIONS`、`INCONCLUSIVE`、`FAIL` 和 `NOT COMPLETED`。测试通过只说明对应测试结果，不自动证明 Independent Verification、Completion 或 Production Readiness。
