# Dependency_Review_Standard.md：HLH AI 软件工程依赖审查标准

> 本文件定义 HLH AI Software Engineering Workflow v3.0 的依赖审查标准。
>
> **所有正式项目新增、升级、删除、替换依赖前，必须遵守本文件。**
>
> **Claude Code 不得未经确认自动安装依赖。**
>
> **依赖审查必须优先考虑安全性、稳定性、长期维护和项目必要性。**

## 2. 依赖审查总原则

### 2.1 不必要的依赖就是风险

每增加一个 npm 包，就增加了：供应链攻击面、构建复杂度、升级负担、许可证风险、团队学习成本。如果一个功能能用 20 行代码自己实现，就不应该引入一个包含 200 个文件的依赖。

### 2.2 稳定性优先于新鲜感

一个刚发布 2 周的包，不管 GitHub 上多少 Star，都不能用于正式项目。选择被人用过、被人测过、被人修过 Bug 的成熟依赖。

### 2.3 官方文档优先于二手教程

判断一个依赖是否可靠，第一来源是官方文档（npm 页面、GitHub README、官方站点），而不是某篇推荐文章或视频教程。

### 2.4 主流生态优先于小众包

同样功能的两个包，选使用者更多、社区更大、更新更频繁的那个。小众包可能随时停止维护。

### 2.5 长期维护优先于短期方便

今天为了省半小时引入了一个看起来方便的包，6 个月后它无人维护、没人修 Bug、跟新版本 Node.js 不兼容——这就是技术债。

### 2.6 安全性优先于开发速度

再方便的工具，如果有已知安全漏洞或不明来源，就不能用。供应链攻击是真实存在的安全威胁。

### 2.7 小功能不引入大框架

只需要一个日期格式化函数，不需要引入 moment.js。只需要一个 HTTP 请求，不需要引入整个 axios 生态（Node.js 18+ 内置 fetch）。按需引入，按功能选包。

### 2.8 新依赖必须说明替代方案

每个新依赖的引入，都必须回答"为什么不用已有的方式解决"。如果已有依赖能满足需求，优先复用。

### 2.9 依赖变更必须写入交付报告

新增了什么、为什么新增、删除了什么、为什么删除、升级了什么、为什么升级——全部记录。

### 2.10 Claude Code 不得自动安装未经确认的依赖

`npm install`、`pnpm add`、`pip install`——这些命令一律需要用户确认后才能执行。这是不可协商的 P2 权限。

## 3. 依赖类型定义

### 3.1 运行时依赖（Runtime Dependencies）

**示例：** `react`、`express`、`@nestjs/core`、`@prisma/client`、`axios`

**特点：** 直接影响项目运行，打包进最终产物。风险较高，升级需谨慎。新增时必须说明对 Bundle 大小、启动速度、内存占用的影响。

### 3.2 开发依赖（Dev Dependencies）

**示例：** `vitest`、`playwright`、`eslint`、`typescript`、`vite`

**特点：** 影响开发、构建、测试，不直接进入运行环境。但仍可能影响构建稳定性和开发体验。CI 环境需要这些依赖，所以不能随意选择。

### 3.3 系统依赖（System Dependencies）

**示例：** Node.js、Python、Docker、PostgreSQL、MySQL、Redis

**特点：** 影响项目运行环境。版本差异可能导致部署失败。必须在 README 中明确版本要求。

### 3.4 外部服务 SDK

**示例：** OpenAI SDK、Anthropic SDK、DeepSeek SDK、阿里云 SDK、腾讯云 SDK、邮件服务 SDK、支付 SDK

**特点：** 涉及 API Key、涉及外部服务调用、涉及费用和数据边界。引入前必须评估：数据传输到哪、费用怎么算、失败时如何降级。

### 3.5 AI / Agent 框架

**示例：** LangChain、LangGraph、Dify、n8n、AutoGen、CrewAI、MCP Server、Skills 工具包

**特点：** 功能强大但复杂度高。容易导致过度架构。必须独立调研、独立实验，验证确实需要后才能引入正式项目。

### 3.6 GitHub 开源项目

**特点：** 可能包含未知脚本、可能有安全风险、可能没有许可证。不得直接运行 `README` 中的安装命令。必须先阅读源码、了解依赖、检查安全风险。

## 4. 依赖风险等级

### D0：低风险

**示例：** 已在项目中使用的小版本修复、文档工具（如 `typedoc`）、类型定义包（`@types/*`）、成熟测试工具的小版本更新

**规则：** 可简要审查，仍需说明目的，仍需记录到交付报告。

### D1：中风险

**示例：** 新增成熟 npm 包、新增成熟开发工具、新增常用 UI 辅助库、新增测试工具

**规则：** 必须说明用途和替代方案、必须检查维护状态、必须等待确认后安装。

### D2：高风险

**示例：** 新增运行时核心依赖、新增 ORM、新增认证库、新增支付 SDK、新增云服务 SDK、新增 AI/Agent 框架、新增数据库相关工具、新增 Docker 镜像、新增 MCP Server

**规则：** 必须详细审查、必须说明安全风险、必须说明部署影响、必须说明卸载方式、必须等待明确授权（P2 级别）。

### D3：默认禁止

**示例：** 来源不明依赖、长期无人维护依赖、绕过平台限制工具、自动刷量/群发/交易工具、盗版组件、要求执行未知脚本的包、要求读取私人文件的包、要求高权限系统访问的包

**规则：** 默认不引入。必须强烈提示风险。不得自动安装。如用户坚持，必须拆分为安全调研步骤，每步确认。

## 5. 新增依赖前必须回答的问题（20 项）

| # | 问题 | 说明 |
|---|------|------|
| 1 | 依赖名称是什么？ | 准确的包名和版本号 |
| 2 | 用来解决什么具体问题？ | 不能用"它很好用"这种模糊理由 |
| 3 | 当前项目已有技术是否能解决？ | 不重复引入功能重叠的依赖 |
| 4 | 是否真的需要依赖？ | 能不能用 20 行代码自己写？ |
| 5 | 是否有更轻量替代方案？ | 同样功能，有没有更小、更简单的包 |
| 6 | 是否在技术白名单内？ | 参考 `Tech_Stack_Standard.md` §9（技术白名单的权威来源）。`references/standards/14-Dependency-Review/dependency-whitelist.md` 作为补充审批记录。 |
| 7 | 是运行时依赖还是开发依赖？ | `dependencies` vs `devDependencies` |
| 8 | 是否活跃维护？ | 最近更新、Star 数、Issue 响应速度 |
| 9 | 是否有官方文档？ | 文档质量直接影响使用和排错效率 |
| 10 | 是否有明显安全风险？ | 已知 CVE、依赖链健康度 |
| 11 | 是否会影响 Build？ | 是否需要额外构建配置 |
| 12 | 是否会影响 Test？ | 是否需要额外的测试配置或 Mock |
| 13 | 是否会影响部署？ | 是否需要系统级依赖或特殊环境 |
| 14 | 是否会影响项目体积？ | 安装大小、打包后大小 |
| 15 | 是否涉及密钥或外部账号？ | 是否需要 API Key、Token |
| 16 | 是否涉及客户数据？ | 数据是否会流经该依赖或外部服务 |
| 17 | 是否方便未来卸载？ | 如果不用了，移除步骤是否简单 |
| 18 | 是否需要更新 README？ | 新增的系统依赖或配置需文档化 |
| 19 | 是否需要更新 .env.example？ | 是否需要新增环境变量 |
| 20 | 是否需要写入 Decision Log？ | 重大依赖引入（D2/D3）必须进入 |

## 6. 新增依赖标准流程

```
提出依赖需求（说明要解决什么问题）
    ↓
判断是否已有替代方案（已有依赖能否解决？能否自己写？）
    ↓
判断是否在技术白名单内（参考 Tech_Stack_Standard.md §9）
    ↓
查询官方文档（理解 API、配置、限制）
    ↓
检查维护活跃度（最近版本时间、GitHub 活跃度、社区大小）
    ↓
检查安全风险（npm audit、已知 CVE、依赖链长度）
    ↓
检查许可证风险（MIT/Apache/BSD/GPL/AGPL/Unknown）
    ↓
检查构建和部署影响（是否需要额外工具或系统依赖）
    ↓
说明安装命令（具体命令、版本号、安装位置）
    ↓
等待用户确认（D0 可简要，D1/D2 必须等待明确确认）
    ↓
安装依赖（执行确认过的安装命令）
    ↓
运行 Build / Test（必须通过，失败进入自动修复）
    ↓
记录交付报告（详见第 21 节）
    ↓
必要时记录 Decision Log（D2 及以上风险等级）
```

### 流程规则

- **不允许跳过审查直接安装。** 先问清楚再动手。
- **不允许为了方便随手安装。** "先装上，以后再说" = 永远不会再说。
- **不允许安装后再解释。** 解释在前，安装在后。
- **不允许安装失败后反复乱试。** 最多 3 轮自动修复，超限停止。
- **不允许用未知脚本安装。** `curl | bash` 永远禁止。

## 7. npm / pnpm / yarn 依赖审查

### 审查内容

| # | 审查项 | 说明 |
|---|--------|------|
| 1 | 包名是否正确 | 是否有拼写仿冒风险（typosquatting） |
| 2 | 是否官方包 | npm 官方源 vs 第三方镜像 |
| 3 | 是否有拼写仿冒风险 | `react` vs `reactt`、`lodash` vs `lodasH` |
| 4 | 周下载量是否合理 | 下载量太低 = 使用人少 = 可能不成熟 |
| 5 | 最近更新时间 | 超过 1 年未更新需特别关注 |
| 6 | GitHub 仓库是否活跃 | Issue 是否有人回复、PR 是否有人合并 |
| 7 | Issue 是否大量未处理 | Open Issue 堆积如山 = 维护不力 |
| 8 | 文档是否清楚 | README 是否完整、API 文档是否可读 |
| 9 | TypeScript 支持情况 | 是否有内置类型或有 `@types/*` 包 |
| 10 | 依赖树是否过重 | 安装一个包带进来 200 个依赖？ |
| 11 | 是否有 install script | postinstall 脚本可能执行任意代码 |
| 12 | 是否访问系统权限 | 是否需要读写文件系统、网络、环境变量 |
| 13 | 是否有已知安全漏洞 | `npm audit` 或 Snyk 检查 |
| 14 | 是否适合当前项目技术栈 | 和已有依赖是否兼容 |

### 安装命令确认

```bash
npm install <package>         # 运行时
npm install -D <package>      # 开发
pnpm add <package>
pnpm add -D <package>
yarn add <package>
yarn add -D <package>
```

### 禁止

- ❌ 安装名字可疑的包（仿冒、拼写变体）
- ❌ 安装长期无人维护的包（> 1 年无更新且 Star < 100）
- ❌ 安装 README 不清楚的包（不知道它能做什么、不知道怎么用）
- ❌ 安装要求执行 `postinstall` 未知脚本的包
- ❌ 安装功能远超需求的大框架（只需一个小工具却引入了整个生态）

## 8. Python pip 依赖审查

适用于数据处理脚本、AI 脚本、爬虫、自动化工具、FastAPI 项目等。

### 审查内容

| # | 审查项 |
|---|--------|
| 1 | 包名是否正确，是否来自 PyPI 官方源 |
| 2 | 是否有官方文档（readthedocs、官方站点） |
| 3 | 是否长期维护（最近 6 个月内有更新） |
| 4 | 是否兼容当前 Python 版本 |
| 5 | 是否有 C 扩展（需要编译器，Windows 可能编译失败） |
| 6 | 是否会影响 Windows 运行（很多 Python 包对 Windows 不够友好） |
| 7 | 是否有已知安全漏洞 |
| 8 | 许可证是否适合项目用途 |

### 安装命令确认

```bash
pip install <package>
```

### 禁止

- ❌ 复制陌生教程里的 `pip install` 命令直接运行
- ❌ 使用来源不明的 `.whl` 文件
- ❌ 使用未知镜像源安装敏感依赖
- ❌ 为一个小脚本引入重型 ML/DL 框架
- ❌ 不记录依赖到 `requirements.txt` 或 `pyproject.toml`

## 9. Docker 镜像审查

Docker 镜像属于高风险依赖（D2）。

### 审查内容

| # | 审查项 | 说明 |
|---|--------|------|
| 1 | 是否官方镜像 | Docker Hub Official Image 标识 |
| 2 | 镜像来源是否可信 | 非官方镜像需额外审查 |
| 3 | Tag 是否固定 | 不默认使用 `latest`，固定到具体版本如 `node:20-alpine` |
| 4 | 镜像体积是否合理 | alpine > slim > full，按需选择 |
| 5 | 是否暴露不必要的端口 | 只暴露必需的端口 |
| 6 | 是否挂载本地目录 | 挂载可能泄露宿主机文件 |
| 7 | 是否需要特权模式 | `--privileged` 极其危险 |
| 8 | 是否读取宿主机敏感目录 | `/var/run/docker.sock` 挂载 = 容器可控制宿主机 |
| 9 | 是否有已知漏洞 | Docker Scout / Trivy 扫描 |

### 规则

- 尽量使用官方镜像（`node`、`postgres`、`redis`、`nginx`）
- 不默认使用 `latest` tag，固定版本
- 不使用来源不明镜像（Docker Hub 上无明确维护者的镜像）
- 不给容器过高权限（不要 `--privileged`，不要挂载 `docker.sock`）
- 不随便挂载宿主机目录
- `docker compose up` 必须确认后才能执行

## 10. GitHub 开源项目审查

引入 GitHub 开源项目前必须逐项检查。

### 审查清单（15 项）

| # | 审查项 |
|---|--------|
| 1 | 项目是否仍在维护（最近 6 个月有 commit） |
| 2 | Star 数不能作为唯一依据（Star 可以买，代码质量买不了） |
| 3 | README 是否清晰（项目是做什么的、怎么安装、怎么用） |
| 4 | 安装方式是否安全（是 `npm install` 还是 `curl | bash`） |
| 5 | 是否要求 `curl | bash` 安装 → 默认拒绝 |
| 6 | 是否要求管理员/root 权限 |
| 7 | 是否要求全盘读取权限 |
| 8 | 是否要求浏览器 Cookie 或本地数据 |
| 9 | 是否要求外部账号 Token |
| 10 | 是否会修改系统配置 |
| 11 | 是否有 LICENSE 文件 |
| 12 | Issue 中是否有安全相关的反馈或警告 |
| 13 | 是否支持 Windows（如果目标环境是 Windows） |
| 14 | 是否适合当前项目目标 |
| 15 | 是否可以只学习其思路和架构，而不是直接安装 |

### 规则

- GitHub 项目优先作为学习对象，其次作为依赖引入。
- **不允许 Claude Code 自动执行 README 中的安装脚本。** 所有安装命令必须经过人工审查。
- 不允许直接运行未知命令。
- 不允许为了"先试试"而污染正式项目环境。
- 有价值的调研结论应沉淀到 `99-Learning/` 或 Decision Log。

## 11. AI / Agent 框架审查

以下技术类别在引入前必须经过严格审查：

**框架示例：** LangChain、LangGraph、Dify、n8n、AutoGen、CrewAI、MCP Server、向量数据库、GraphRAG、多 Agent 编排框架

### 审查问题（10 项）

| # | 问题 |
|---|------|
| 1 | 它解决什么具体业务问题？——不是"它很强大"，是"它让 X 流程从 Y 分钟降到了 Z 分钟" |
| 2 | 当前 Prompt + Workflow 是否已经能解决？——不要跳过简单方案直接追复杂框架 |
| 3 | 是否会增加维护成本？——框架升级、Breaking Change、依赖冲突 |
| 4 | 是否会增加部署复杂度？——是否需要额外服务、额外基础设施 |
| 5 | 是否会导致项目难以理解？——接手的人能否看懂这套 Agent 编排 |
| 6 | 是否适合 Claude Code 生成稳定代码？——AI 生成该框架代码的准确率如何 |
| 7 | 是否会绑定某个生态？——换框架的成本有多高 |
| 8 | 是否会影响中国网络环境可用性？——是否需要科学上网 |
| 9 | 是否涉及外部数据传输？——用户数据是否发送到第三方 |
| 10 | 是否需要额外密钥或付费账号？ |

### 规则

- 当前阶段优先级：Prompt → Workflow → Skills → MCP → Subagents → Multi-Agent（逐级演进）
- **不允许一开始就引入复杂 Agent 框架**——跳过前面的阶段直接追最后一步，就是空中楼阁
- AI 框架必须服务业务流程，不是服务炫技

## 12. MCP 依赖审查

MCP Server 如在 legacy source repository 中进行引入审查，必须先登记到该仓库的 `06-MCP/mcp_registry.md`；MCP 不属于当前 v3.2 Plugin Runtime。

### 审查内容（15 项）

| # | 审查项 |
|---|--------|
| 1 | MCP 名称和来源（官方/社区/个人） |
| 2 | MCP 用途（解决什么具体问题） |
| 3 | 需要什么权限（读文件？写文件？执行命令？网络访问？） |
| 4 | 是否读取项目之外的文件 |
| 5 | 是否连接外部账号（GitHub、数据库、云服务） |
| 6 | 是否访问网络 |
| 7 | 是否访问数据库 |
| 8 | 是否需要 API Key |
| 9 | 是否会执行系统命令 |
| 10 | 权限是否可以限制（能不能只给只读权限） |
| 11 | 是否可以随时关闭（出问题时能不能停） |
| 12 | 是否可以回滚（移除 MCP 后项目是否正常） |

### 规则

- 未登记 MCP 不得进入任何项目。
- 未批准（Approved）MCP 不得进入正式项目。

## 14. 许可证与合规风险

依赖引入前必须关注许可证类型。

| 许可证 | 风险 | 说明 |
|--------|------|------|
| MIT | ✅ 低风险 | 宽松，可商用 |
| Apache-2.0 | ✅ 低风险 | 宽松，含专利授权 |
| BSD | ✅ 低风险 | 宽松 |
| ISC | ✅ 低风险 | 类似 MIT |
| GPL | ⚠️ 中高风险 | 传染性——项目可能也被要求开源 |
| AGPL | ⚠️ 高风险 | 网络使用也触发传染条款 |
| Commercial | ⚠️ 需审查 | 看具体条款 |
| Unknown | ❌ 高风险 | 不知道能不能商用 = 不能商用 |

### 规则

1. MIT / Apache-2.0 / BSD / ISC 通常可直接使用。
2. GPL / AGPL 可能影响商业项目——引入前必须了解其传染性条款。
3. **Unknown License（无 LICENSE 文件）默认视为高风险。** 不用于商业项目。
4. **盗版组件禁止使用。** 任何形式的盗版软件、破解工具不进入体系。
5. 商业项目不得随意使用许可证不明的代码。
6. 从开源项目复制代码必须保留原始版权声明。
7. 依赖许可证风险应写入审查记录，D2 级别以上必须记录 Decision Log。

## 15. 依赖升级规则

依赖升级也属于风险操作。升级可能引入 Breaking Change、新的 Bug、安全漏洞、或依赖冲突。

### 升级前必须确认

| # | 确认项 |
|---|--------|
| 1 | 为什么升级？（安全修复？Bug 修复？新功能？"就是想升级"？） |
| 2 | 是否修复已知安全漏洞（CVE）→ 高优先级 |
| 3 | 是否修复已知 Bug → 中优先级 |
| 4 | 是否为了新功能 → 低优先级，需评估是否真的需要 |
| 5 | 是否有 Breaking Change（查看 CHANGELOG 和 Migration Guide） |
| 6 | 是否影响 Build？ |
| 7 | 是否影响 Test？ |
| 8 | 是否影响部署？ |
| 9 | 是否影响现有代码？（API 是否变化） |
| 10 | 是否有回滚方式？（`git revert` + 重新安装旧版本） |

### 禁止

- ❌ 一次性升级所有依赖（"`npm update` 一下" = 引入未知风险）
- ❌ 为了"保持最新"盲目升级（最新 ≠ 最稳）
- ❌ 不看 CHANGELOG 就升级大版本（Major 版本大概率有 Breaking Change）
- ❌ 升级失败后乱改代码来适配（先理解为什么失败，再决定怎么处理）
- ❌ 未测试就提交升级

## 16. 依赖删除规则

删除依赖前必须确认不再被任何地方引用。

### 删除前必须确认

| # | 确认项 |
|---|--------|
| 1 | 是否仍被代码引用？（全局搜索包名） |
| 2 | 是否被构建脚本引用？（`package.json` scripts、`scripts/` 目录） |
| 3 | 是否被测试引用？ |
| 4 | 是否被文档引用？（README、setup 文档） |
| 5 | 是否被模板引用？ |
| 6 | 是否有替代方案？（删除后功能如何实现） |
| 7 | 是否需要更新 `package.json`？ |
| 8 | 是否需要更新 lock 文件？（删除后需重新生成 lock） |
| 9 | 是否需要更新 README？ |
| 10 | 是否需要更新交付报告？ |

### 规则

- 删除依赖必须先全局搜索引用，确认无遗漏。
- 删除依赖后必须运行 Build / Test 确认没有破坏。
- 删除失败不得通过删除功能代码来"解决"。
- 删除依赖必须说明回滚方式（重新 `npm install` 原版本即可）。

## 17. Lock 文件规则

| 包管理器 | Lock 文件 |
|----------|-----------|
| npm | `package-lock.json` |
| pnpm | `pnpm-lock.yaml` |
| yarn | `yarn.lock` |

### 规则

1. **正式项目应提交 lock 文件到 Git。** Lock 文件确保所有人安装到相同版本的依赖。
2. **不应随意删除 lock 文件。** 删除后重新生成可能引入不同版本的依赖。
3. **不应混用多个包管理器。** 一个项目只有一个 lock 文件。
4. **不应同时存在 `package-lock.json` 和 `pnpm-lock.yaml`**，除非有明确原因并记录在案。
5. **修改依赖后 lock 文件的变化必须进入同一个 commit。** 不能只改 `package.json` 不改 lock。
6. **仅文档修改不应改变 lock 文件。** 如果 lock 文件无意中被改动，应 revert。
7. **Claude Code 不得无理由删除或重建 lock 文件。**
8. **包管理器选择必须在 README 或 CLAUDE.md 中说明。**

## 18. 包管理器选择规则

### 默认建议

| 项目类型 | 推荐 |
|----------|------|
| 长期新项目 | pnpm 或 npm，项目确定后固定不变 |
| 简单/MVP 项目 | npm（零配置，Node.js 自带） |
| 团队/商业项目 | 根据客户环境和团队已有习惯决定 |
| 已有项目 | 沿用项目现有包管理器，不随意切换 |

### 规则

1. **一个项目只能选择一个主包管理器。** npm **或** pnpm **或** yarn，三者选一。
2. **不得 npm、pnpm、yarn 混用。** 混用会导致 lock 文件冲突和依赖版本不一致。
3. **切换包管理器属于 P2 中高风险。** 需要明确理由。
4. **切换前必须删除旧 lock 文件并说明原因。** 记录在 Decision Log。
5. **切换后必须完整 Build / Test。** 确认依赖安装和构建无异常。
6. **包管理器选择应写入 README（安装步骤）和 CLAUDE.md（技术栈）。**

## 19. 依赖与安全扫描

### 可用工具（当前阶段不强制，但建议了解）

- `npm audit` — npm 内置安全审计
- `pnpm audit` — pnpm 内置安全审计
- GitHub Dependabot — 自动检测依赖漏洞并提 PR
- Snyk — 第三方依赖安全扫描
- OSV Scanner — Google 开源漏洞扫描

### 规则

1. **安全扫描结果不能盲目自动修复。** `npm audit fix` 可能升级依赖大版本，引入 Breaking Change。
2. **`audit fix` 可能引入破坏性升级，必须谨慎。** 先看具体是什么漏洞、影响什么、修复版本是否兼容。
3. **高危漏洞（Critical / High）必须优先处理。** 不能视而不见。
4. **低危漏洞（Low / Moderate）根据项目阶段和风险判断。** 可以排期处理。
5. **商业项目交付前必须至少检查明显依赖风险。** Run `npm audit` 并检查结果。
6. **Agent / MCP / AI 项目涉及外部服务时依赖风险更高。** 增加审查频率。

### 禁止

- ❌ 不看结果直接 `npm audit fix --force`（`--force` 可能安装不兼容版本）
- ❌ 为了消除安全提示而升级大版本导致项目崩坏
- ❌ 忽略高危运行时依赖漏洞（"反正只在本地用" ≠ 安全）

## 20. Claude Code 权限规则

## 25. 最终默认结论

1. **新增依赖默认不是小事。** 每个依赖都是一份长期责任。
2. **Claude Code 不得未经确认安装依赖。** P2 权限，必须用户确认。
3. **npm / pnpm / pip / Docker / MCP / Skills / GitHub 项目都属于依赖审查范围。** 不遗漏任何一种。
4. **当前主技术栈以已批准白名单为主。** 参考 `Tech_Stack_Standard.md` §9。
5. **当前阶段不引入复杂 Agent 框架。** 先 Prompt，再 Workflow，逐级演进。
6. **当前阶段不自动安装 MCP。** 先调研、测试、批准，再考虑引入。
7. **当前阶段 GitHub 项目优先作为学习对象，不优先作为依赖安装。**
8. **依赖变更必须 Build / Test 通过后才能提交。**
9. **依赖变更必须写入交付报告。** 新增了什么、为什么、安不安全。
10. **依赖越少，系统越容易长期维护。** 精简 > 堆砌。
