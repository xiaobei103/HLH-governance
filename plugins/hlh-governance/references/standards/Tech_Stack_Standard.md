# Tech_Stack_Standard.md：HLH AI 软件工程技术栈选择标准

> 本文件定义 HLH AI Software Engineering Workflow v3.0 的技术栈选择标准。
>
> 技术栈选择必须服务于：项目长期维护、稳定交付、中国市场需求、AI 扩展能力和求职作品集价值。
>
> **不允许为了追热点随意更换技术路线。**

---

## 1. 文档定位

本文件是 `01-Standards/` 下的技术栈选择标准。

### 本文件回答的问题

- 什么项目应该用什么技术栈？
- 什么情况下用 PostgreSQL？什么情况下用 MySQL？什么情况下用 SQLite？
- 什么情况下用 NestJS？什么情况下可以用 Express？
- 什么情况下选择 React？什么情况下考虑小程序 / App？
- 什么情况下允许引入 AI / Agent / MCP / Skills？
- 什么情况下禁止引入复杂技术？

### 本文件不负责

- 具体项目代码实现 → `Coding_Workflow.md`
- 具体部署细节 → `Delivery_Standard.md`
- 具体数据库迁移步骤 → `Database_Standard.md`
- Claude Code 编码流程 → `CLAUDE_MASTER.md`
- 商业验证流程 → `Business_Workflow.md`

## 2. 技术选型总原则

### 2.1 稳定性优先于新鲜感

一个技术再新、再热，如果生产环境不稳定、生态不成熟、出了问题找不到答案，就不能用于正式项目。新技术可以学习，但不能拿正式项目当实验品。

### 2.2 安全性优先于自动化程度

自动化程度越高，攻击面和失误面越大。每增加一层自动化（Agent、MCP、Hooks），必须对应增加安全约束。安全性是不可谈判的底线。

### 2.3 长期维护优先于短期开发速度

今天省的一个小时，半年后可能要花十个小时来还。技术选择必须考虑：半年后别人（或自己）还能不能看懂、能不能改、能不能部署。

### 2.4 中国市场适配优先于国外潮流

技术选型以中国大陆实际可用的服务、网络环境、合规要求和用户习惯为准。无法在中国大陆正常使用的技术方案不得作为国内商业项目的首选。

### 2.5 项目类型决定技术栈，不是一套技术打天下

AI 产品、CRM、网站、本地工具、小程序——它们的需求完全不同。不存在一个"最佳技术栈"适合所有项目。

### 2.6 AI 能力必须服务业务流程，不为了炫技而引入

不应因为"我可以加个 Agent"就给 CRM 加 Agent。AI 的引入必须有明确的业务流程需求、用户价值、失败处理和人工兜底。

### 2.7 个人学习可以探索，正式项目必须保守

学习项目可以试新技术、试新框架、试新工具。正式项目（接单、产品、求职作品集）必须使用经过验证的稳定技术栈。

### 2.8 技术栈变更必须记录 Decision Log

从 SQLite 换到 PostgreSQL、从 Express 换到 NestJS——这些都不是可以随手做的决定。每次变更必须有记录：为什么变、从什么变到什么、影响范围、回滚方案。

### 2.9 新依赖必须经过 Dependency Review

每引入一个 npm 包或 Python 包，都增加一份供应链风险和项目复杂度。新增依赖前必须说明用途、替代方案和风险。

### 2.10 不允许为了追热点随意推翻主技术路线

某个新技术在网上火了、某个框架发了大版本、某个工具被吹得很厉害——这些都不是更换技术栈的理由。

## 3. 默认主技术栈

### 3.1 前端默认栈

**推荐：React + TypeScript + Vite + Ant Design**

| 技术 | 用途 | 选择理由 |
|------|------|----------|
| **React** | UI 框架 | 国内外生态最成熟，社区最大，求职市场认可度最高 |
| **TypeScript** | 类型系统 | 有利于长期维护、AI 理解代码、减少低级 Bug |
| **Vite** | 构建工具 | 启动快、开发体验好、配置简单、社区活跃 |
| **Ant Design** | UI 组件库 | 适合后台系统、CRM、管理面板、数据看板等企业级场景 |

**适用场景：**
- 管理后台、CRM、AI Operating System、Agent 控制台
- 数据看板、企业内部工具
- 求职作品集项目

### 3.2 后端默认栈

**长期项目推荐：NestJS + TypeScript**

| 技术 | 用途 | 选择理由 |
|------|------|----------|
| **NestJS** | 后端框架 | 架构规范、模块化清晰、TypeScript 原生、适合大型项目演进 |
| **TypeScript** | 类型系统 | 前后端统一语言、AI 友好、可维护性高 |

**轻量项目可选：Express + TypeScript（或 JavaScript）**

| 场景 | 选择 |
|------|------|
| 长期 AI 产品、SaaS、CRM、多模块系统、权限复杂系统、团队协作项目 | NestJS |
| 快速 MVP、本地工具、小型接口服务、临时验证项目、旧项目维护 | Express |

**原则：** 长期项目优先 NestJS，快速验证可用 Express。不允许在同一项目中无理由混用多个后端框架。

### 3.3 数据库默认栈

| 数据库 | 适用场景 | 选择理由 |
|--------|----------|----------|
| **PostgreSQL** | 长期 AI 产品、Agent 系统、复杂数据、向量扩展 | 功能最强、扩展性最好、支持 pgvector、适合 AI 数据场景 |
| **MySQL** | 国内商用系统、管理后台、外包接单、CRM | 中国普及率高、企业接受度高、运维人员熟悉 |
| **SQLite** | 单机工具、快速 MVP、本地试用版、小型个人项目 | 零部署、简单、本地运行方便 |

**原则：**
- 长期 AI 产品 → PostgreSQL
- 国内普通商用 → MySQL
- 快速验证/本地工具 → SQLite
- **不允许把 SQLite Demo 直接当正式商业系统交付。**

### 3.4 ORM 默认栈

**推荐：Prisma**

| 优势 | 说明 |
|------|------|
| TypeScript 体验好 | 类型安全的查询 API，编译时发现错误 |
| Schema 清晰 | 单文件 `schema.prisma` 定义全部数据模型 |
| AI 友好 | 结构化的 schema 易于 Claude Code 理解和生成 |
| 迁移流程清楚 | `prisma migrate dev` 生成可审查的迁移文件 |
| 多数据库支持 | 同一套 API 操作 PostgreSQL / MySQL / SQLite |

**限制：**
- Prisma migration 属于 R2 高风险，执行前必须确认
- 数据库变更必须走 `Database_Standard.md` 流程
- Claude Code 不得自动修改真实数据

### 3.5 测试默认栈

| 工具 | 用途 | 说明 |
|------|------|------|
| **Vitest** | 单元测试、工具函数测试、后端服务测试 | 快、兼容 Vite 生态、API 兼容 Jest |
| **Playwright** | E2E 测试、页面流程测试、核心业务回归 | 稳定、多浏览器、适合关键流程验收 |

**原则：**
- 长期项目必须逐步建立测试
- MVP 可先保留测试入口（有 test 命令，测试可少但不可无）
- 没有测试必须在交付报告中标记风险 ⚠️

### 3.6 部署默认栈

| 方案 | 适用场景 |
|------|----------|
| **Docker + Linux + Nginx** | 长期产品部署 |
| **阿里云 / 腾讯云 / 宝塔面板** | 国内商业项目 |
| **本地运行 + GitHub README 演示** | 学习/求职项目 |
| **静态部署（Vercel / GitHub Pages）** | 纯前端展示项目 |

**原则：**
- 部署属于 P3 高风险，Claude Code 不得自动部署生产环境
- 部署必须有回滚方案
- 部署文档必须齐全

## 4. 项目类型与技术栈选择

### 4.1 长期 AI 产品

**示例：** AI Operating System、Web Research Agent、Content Agent、Stock Agent

**推荐技术栈：**

| 层级 | 选择 |
|------|------|
| 前端 | React + TypeScript + Vite + Ant Design |
| 后端 | NestJS + TypeScript |
| 数据库 | PostgreSQL |
| ORM | Prisma |
| 缓存 | Redis（按需） |
| 测试 | Vitest + Playwright |
| 部署 | Docker + Linux + Nginx |
| AI 扩展 | MCP / Skills / Subagents（后期引入） |

**原则：**
- 优先 PostgreSQL（扩展性、AI 兼容性）
- 保留 Agent / Workflow / MCP 扩展空间但不一开始就全部加入
- 不一开始做过度自动化
- 不一开始引入多个复杂 Agent 框架堆叠

### 4.2 国内普通商用项目

**示例：** CRM、管理后台、数据管理系统、企业内部系统、小老板定制工具

**推荐技术栈：**

| 层级 | 选择 |
|------|------|
| 前端 | React + TypeScript + Ant Design |
| 后端 | NestJS 或 Express（按项目规模） |
| 数据库 | MySQL |
| ORM | Prisma |
| 测试 | Vitest（按需） |
| 部署 | Docker + 国内云服务器（按需） |

**原则：**
- 优先稳定交付和客户可维护性
- 可优先 MySQL（中国企业环境兼容性更好）
- 不强行加入 AI（没有明确需求就不加）
- 不为了技术炫技增加客户维护成本

### 4.3 快速 MVP / 本地工具

**示例：** 单机工具、数据处理工具、快速验证系统、小型爬取整理工具

**推荐技术栈：**

| 层级 | 选择 |
|------|------|
| 前端 | React 或简单 HTML/CSS/JS |
| 后端 | Express |
| 数据库 | SQLite |
| ORM | Prisma 或 better-sqlite3 |

**原则：**
- 可以降低复杂度以换取速度
- 仍必须有 Git、README.md、CLAUDE.md、交付说明
- 不能直接把 MVP 当成正式商业系统交付

### 4.4 网站接单项目

**示例：** 企业官网、个人作品站、落地页、活动页、简单后台

**推荐技术栈：**
- React / Next.js / 静态站点（按需选择）
- 样式按需选择 Tailwind CSS 或 Ant Design
- 简单后端可用 Express（不需要时可不做后端）
- 数据库按需求选择 SQLite / MySQL

**原则：**
- 以交付速度和稳定为主
- 不引入过重架构——一个小网站不需要 NestJS + PostgreSQL + Redis + Docker
- 客户需要后台时再引入后端和数据库，不要提前过度设计

### 4.5 App / 小程序项目

**示例：** 微信小程序、移动端工具、轻量 App

**推荐方向：**
- 微信小程序原生 / Taro / uni-app（视项目确定）
- 后端优先 NestJS 或 Express
- 数据库优先 MySQL 或 PostgreSQL

**原则：**
- 当前阶段先不主攻 App（优先 Web 全栈）
- 小程序适合国内移动端场景
- 但开发、审核、登录、支付、隐私合规风险更高
- 必须先验证移动端需求真实存在，再决定开发

### 4.6 学习研究项目

**示例：** GitHub 开源项目研究、MCP 测试、Skills 测试、Agent 框架调研

**原则：**
- 独立实验目录，不混入正式项目
- 不污染项目模板
- 有价值的结论进入 `99-Learning/` 或 Decision Log
- 学习项目的代码不能直接当正式产品交付

## 5. 数据库选择标准

### 5.1 PostgreSQL

**适用：** AI 产品、Agent 系统、复杂数据关系、需要向量扩展（pgvector）、长期 SaaS、多模块系统

**优势：** 功能最强、扩展性最好、支持 AI 数据场景和复杂查询

**限制：** 国内普通小企业理解成本略高、运维比 SQLite 复杂、对新手配置有门槛

**结论：** 长期 AI 项目默认优先 PostgreSQL。

### 5.2 MySQL

**适用：** 国内普通商用系统、企业管理后台、外包接单、CRM、客户已有 MySQL 环境、传统业务系统

**优势：** 中国市场普及率极高、企业接受度高、运维人员熟悉、国内云服务支持好

**限制：** AI/向量扩展不如 PostgreSQL 方便、复杂数据场景不一定是第一选择

**结论：** 国内普通商用项目默认优先 MySQL。

### 5.3 SQLite

**适用：** 单机工具、快速 MVP、本地试用版、小型个人项目、数据量很小的工具

**优势：** 零部署、简单、本地运行方便、适合快速验证和原型开发

**限制：** 不适合多人并发、不适合正式 SaaS、不适合复杂权限系统、数据迁移和备份必须谨慎

**结论：** SQLite 只适合本地工具和快速验证 MVP。不应直接作为正式多人商业系统的数据库。

## 6. 后端框架选择标准

### 6.1 NestJS

**适用：** 长期项目、企业级系统、AI Operating System、管理后台、多模块业务、权限复杂系统、需要团队协作和长期演进的项目

**优势：** 架构规范（Module/Controller/Service）、TypeScript 原生支持、模块化清晰、依赖注入、适合大型项目演进、社区活跃

**限制：** 初始复杂度高于 Express、对新手有学习成本、小型项目可能过度设计

**结论：** 长期主力后端框架优先 NestJS。

### 6.2 Express

**适用：** MVP、本地工具、小型接口服务、快速验证、旧项目维护

**优势：** 极简、快速上手、学习成本低、适合快速试错、灵活度极高

**限制：** 大项目容易结构混乱、缺乏内置规范约束、需要额外约定和规范

**结论：** Express 适合快速验证和小型项目。大型长期项目不将 Express 作为默认首选。

## 7. 前端选择标准

### 默认优先：React + TypeScript + Vite + Ant Design

**适用：** 后台系统、CRM、AI 控制台、数据看板、内部工具、求职作品集

### 何时考虑其他方案

| 需求 | 推荐 | 说明 |
|------|------|------|
| 需要 SEO / SSR | Next.js | 官网、内容型网站、需要服务端渲染 |
| 自定义视觉效果强的页面 | Tailwind CSS | 官网、落地页、营销页面 |
| 用户主要在微信生态 | 微信小程序 | 需先验证移动端需求真实存在 |
| 需要跨平台移动端 | Taro / uni-app | 先评估是否真的需要，再选框架 |

**原则：**
- 管理系统优先 Ant Design（开箱即用的企业级组件）
- 官网落地页可用 Tailwind CSS（灵活度高）
- 不为了流行强行换 UI 方案
- 不在同一项目中混用过多 UI 框架（保持一致性）

## 8. AI / Agent 技术引入标准

### 允许引入 AI / Agent 的条件

必须同时满足：

1. 业务流程确实需要自动分析、自动决策或自动执行
2. 用户能理解 AI 为业务流程带来的具体价值
3. 有明确的输入、输出和失败处理机制
4. 有人工确认节点（Agent 不能全自动运行无人监督）
5. 有完整的操作日志记录
6. 有回滚或撤销方式
7. 不涉及未经授权的数据读取
8. 不涉及 P3 级别的高风险自动操作

### 当前阶段优先级（从低到高逐级演进）

```
Prompt（用 Prompt 模板模拟 Agent 行为）
    ↓ 验证稳定后
Workflow（将验证过的 Prompt 流程化为工作流）
    ↓ 验证稳定后
Skills（将工作流封装为可复用的 Skill）
    ↓ 验证稳定后
MCP（通过 MCP 连接外部工具和数据源）
    ↓ 验证稳定后
Subagents（用 Subagent 实现角色分工）
    ↓ 验证稳定后
Multi-Agent（多个 Agent 在规则下协作）
```

**原则：**
- 先从 Prompt 开始，不要跳过前面的阶段直接追最后的多 Agent
- 每个阶段跑通了、验证了、稳定了，再进入下一个阶段
- 不允许一开始追求全自动——全自动等于全失控

### 禁止

- 为了显得高级强行加 Agent
- 让 Agent 无边界操作电脑
- 让 Agent 自动连接外部账号
- 让 Agent 自动处理真实客户数据
- 让 Agent 自动交易、支付、群发、投递

## 9. 技术白名单

> **说明：** 本文件是技术路线与技术白名单的权威来源。**新依赖是否允许进入项目，必须继续走 `Dependency_Review_Standard.md` 的审查流程。** 技术白名单定义"什么技术可以用"，Dependency_Review_Standard 定义"怎么审查和批准引入"。

### 9.1 当前推荐白名单（可直接使用）

| 类别 | 技术 | 备注 |
|------|------|------|
| **前端框架** | React、Next.js（按需） | React 为主，Next.js 按场景选用 |
| **语言** | TypeScript | 全栈统一语言 |
| **构建** | Vite | 默认构建工具 |
| **UI 库** | Ant Design、Tailwind CSS | Ant Design 用于后台，Tailwind 用于官网 |
| **后端框架** | NestJS、Express | NestJS 为主，Express 用于轻量场景 |
| **运行时** | Node.js | 统一运行时 |
| **数据库** | PostgreSQL、MySQL、SQLite | 按项目类型选择 |
| **ORM** | Prisma | 默认 ORM |
| **测试** | Vitest、Playwright | 单元测试 + E2E |
| **部署** | Docker、Linux、Nginx | 按需引入 |
| **版本管理** | Git、GitHub、Gitee、GitLab | 按项目性质选择托管平台 |
| **AI 扩展** | Prompt、Workflow、Skills、MCP、Subagents | 逐级演进，不一步到位 |

### 9.2 谨慎引入清单（必须先评审，不可直接使用）

以下技术不是禁止，但**引入前必须走第 10 节的新技术引入流程**：

- **Agent 框架：** LangChain、LangGraph、Dify、n8n、AutoGen、CrewAI
- **数据相关：** 向量数据库（Pinecone、Weaviate、Qdrant、Milvus）、GraphRAG
- **基础设施：** Kubernetes（K8s）、微服务架构、消息队列（RabbitMQ、Kafka）
- **跨平台：** Electron、Flutter、React Native

**理由：** 这些技术可能在某些场景下有巨大价值，但也显著增加系统复杂度。必须先判断项目是否真的需要，而不是"用上显得高级"。

### 9.3 默认禁止随意引入

| 类别 | 示例 |
|------|------|
| 来源不明包 | 非 npm/PyPI 官方源的依赖 |
| 无人维护包 | 超过 1 年未更新且 Star < 100 的包 |
| 小众框架 | 社区极小的前端/后端框架 |
| 黑盒平台 | 无法审查代码的低代码平台 |
| 盗版组件 | 任何破解或盗版软件 |
| 违规工具 | 绕过平台限制的工具、自动刷量工具、自动群发工具、自动交易工具 |
| 未验证脚本 | 来源不明的 GitHub 仓库中的安装/运行脚本 |

## 10. 新技术引入流程

任何新技术进入正式项目前，必须走以下流程：

```
发现新技术
    ↓
记录来源（GitHub 链接、文章、文档）
    ↓
判断解决什么问题（它能解决什么当前解决不了的问题？）
    ↓
查官方文档（了解基本概念、API、限制）
    ↓
查维护活跃度（最近更新时间、Star 数、Issue 响应、社区活跃度）
    ↓
查安全风险（是否有已知 CVE？依赖链是否健康？）
    ↓
查中国环境可用性（是否需要科学上网？国内镜像是否可用？）
    ↓
查是否替代现有方案（是否已有白名单中的技术能解决同样问题？）
    ↓
做独立实验（在 Demo 项目或 99-Learning 中验证）
    ↓
写调研结论（适用场景、优势、风险、替代方案对比）
    ↓
决定是否进入白名单
    ↓
记录 Decision Log
```

### 必须回答的 10 个问题

1. 它解决什么具体问题？——不能用"它很强大"这种模糊理由
2. 当前技术栈是否已经能解决？——避免重复引入
3. 引入后增加什么复杂度？——学习成本、维护成本、部署成本
4. 是否影响部署？——是否需要额外的系统依赖或基础设施
5. 是否影响安全？——是否有已知漏洞、是否扩大了攻击面
6. 是否适合中国网络环境？——是否需要 VPN、是否有国内镜像
7. 是否适合 Claude Code 稳定生成代码？——AI 能否理解其 API 并生成可靠代码
8. 是否有长期维护风险？——作者是否可能弃坑、社区是否足够大
9. 是否值得进入正式模板？——是否应该长期作为推荐技术
10. 如果未来废弃，如何替换？——退出成本是多少

## 11. 技术栈变更规则

技术栈变更属于 P2 高风险。以下变更行为必须停止、评估并等待确认：

- SQLite → PostgreSQL（或反向）
- SQLite → MySQL（或反向）
- Express → NestJS（或反向）
- React → 其他前端框架
- Ant Design → 其他 UI 框架
- 引入 Agent 框架
- 引入 MCP
- 引入 Docker
- 引入云服务（首次）
- 引入支付功能
- 引入登录权限系统
- 引入小程序 / App

### 变更规则

1. **不允许在开发中途随意换栈。** 功能做了一半说"换成另一个框架更好"，这种变更成本极高。
2. **不允许为了一个功能换整个架构。** 一个功能不合适，就改那个功能，不推倒整个系统。
3. **不允许因为网上热门就换技术。** 热门的生命周期通常不到 6 个月，而项目要维护数年。
4. **技术栈变更必须写入 Decision Log。** 记录：原因、替代方案对比、影响范围、迁移成本、回滚方案。
5. **技术栈变更必须说明迁移成本和回滚方案。** 如果变更失败如何回退。

## 12. 中国市场适配原则

中国市场项目必须额外考虑以下 10 点：

| # | 考量点 | 说明 |
|---|--------|------|
| 1 | 客户是否能部署 | 客户有没有服务器？懂不懂 Docker？会不会配环境？ |
| 2 | 客户是否能维护 | 交付后客户能不能自己日常操作？还是必须你长期维护？ |
| 3 | 客户是否接受该技术 | 客户的技术团队是否认可你的技术栈？ |
| 4 | 网络环境是否稳定 | 是否依赖被墙的国外服务？npm 安装是否稳定？ |
| 5 | 是否依赖国外服务 | GitHub、Vercel、OpenAI API、Supabase 等在国内可能不稳定或不可用 |
| 6 | 是否涉及合规风险 | 数据存储、用户隐私、支付牌照、ICP 备案 |
| 7 | 是否方便交付 | 能否打包成一键部署？交付后客户能不能用起来？ |
| 8 | 是否方便售后 | 出问题时你能不能远程排查？客户能不能配合你？ |
| 9 | 是否方便接手 | 如果别人接手维护，能不能看懂你的技术方案？ |
| 10 | 是否方便写进简历/作品集 | 这个技术在国内求职市场上的认可度如何？ |

### 具体原则

- 国内普通企业项目优先 MySQL（客户运维人员更熟悉）
- 国内客户项目慎用强依赖国外服务（GitHub Actions、Vercel、OpenAI API 等可能不稳定）
- GitHub 适合学习展示和求职作品集，商业交付可考虑 Gitee 或客户自建 GitLab
- 海外 AI 服务用于学习可以，客户真实数据接入必须谨慎评估合规和数据安全风险
- 客户项目不应强依赖用户无法正常访问的服务

## 13. 求职作品集技术栈原则

求职作品集项目应优先展示以下能力和技术：

1. **TypeScript** — 静态类型意识
2. **React** — 主流前端框架的熟练使用
3. **NestJS 或 Express** — 后端架构的理解
4. **PostgreSQL / MySQL / SQLite** — 能根据场景选择合适的数据库并能解释理由
5. **Prisma** — 现代 ORM 的使用和 schema 设计
6. **API 设计** — RESTful 接口的合理设计
7. **数据库设计** — 表结构、关系、索引的合理规划
8. **测试意识** — 至少有针对关键逻辑的测试
9. **Git 记录** — 清晰的 commit 历史和有意义的信息
10. **文档能力** — README、CHANGELOG、技术说明
11. **AI Coding 工作流** — 能说明 Claude Code 如何参与了开发过程
12. **Agent / Workflow / MCP 的合理理解** — 能讲清楚 AI Agent 的能力和边界

### 作品集要求

- 不必堆砌技术名词（"我用过 20 个框架"不如"我能解释为什么选这 3 个"）
- 必须能解释为什么选择这些技术（每个技术选择都有理由）
- 必须有 README（面试官第一个看的就是 README）
- 必须有截图或演示（能看到的东西比描述更有说服力）
- 必须能讲清楚项目边界和迭代过程（从 0 到 1，每个版本做了什么）
- 必须能说明 Claude Code 如何参与开发（AI 协作能力是加分项）

## 14. 不同阶段技术复杂度控制

### 当前阶段（Phase 1 — 规范搭建）

**允许：**
- 写规范、写模板、写 Standards
- 使用 Git 管理文档
- 使用 Claude Code 辅助文档和代码
- 使用 React / Express / SQLite 维护已有项目
- 学习 NestJS / PostgreSQL / Prisma（Demo 项目验证）

**禁止：**
- 立即引入复杂 MCP
- 立即开启多 Agent 并发
- 立即上 Kubernetes
- 立即做大型 SaaS
- 立即做复杂权限系统
- 立即自动化操作外部账号

### MVP 阶段

**允许：** 简化技术栈、少量手动流程、简单数据库、基础测试、简单部署

**禁止：** 过度架构、过度自动化、过度抽象、把所有未来功能都塞进第一版

### 正式产品阶段

**必须逐步补齐：**
- 登录和权限系统
- 数据备份机制
- 错误日志和监控
- 测试覆盖（单元 + E2E）
- 部署文档
- 安全审查
- 交付报告
- 版本管理规范

## 16. 禁止事项

| # | 禁止事项 | 原因 |
|---|----------|------|
| 1 | 禁止为了追热点更换技术栈 | 热点会变，稳定是基础。一个热门的框架可能 6 个月后无人维护 |
| 2 | 禁止为了炫技引入复杂架构 | 微服务、K8s、消息队列——不是每个项目都需要 |
| 3 | 禁止没有验证需求就做大型系统 | 先验证痛点，再做 MVP，再逐步扩展 |
| 4 | 禁止为小功能引入大框架 | 一个按钮不需要引入一个组件库，一个脚本不需要引入一个框架 |
| 5 | 禁止正式项目使用来源不明依赖 | 供应链安全是真实存在的风险 |
| 6 | 禁止客户项目强依赖不可访问的服务 | 客户的业务不能因为 GitHub 挂了就停了 |
| 7 | 禁止把 SQLite Demo 当正式多人系统 | SQLite 的并发能力、部署方式都不适合多人商业系统 |
| 8 | 禁止在没有测试和回滚的情况下修改数据库 | 数据是项目最重要的资产，不可逆操作必须谨慎 |
| 9 | 禁止让 Claude Code 自动决定技术栈 | 技术栈选择是工程决策，不是 AI 可以自主决定的 |
| 10 | 禁止把技术成就感当成商业价值 | 你觉得酷 ≠ 用户需要。用 Business Workflow 验证 |
