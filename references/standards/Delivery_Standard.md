# Delivery_Standard.md：HLH AI 软件工程交付标准

> 本文件定义 HLH AI Software Engineering Workflow v3.2 的交付标准。
>
> **所有正式项目、商业项目、求职作品集项目和 AI Coding 任务，必须遵守本文件。**
>
> **交付不是"代码写完"，而是范围明确、验证完成、风险说明、可回滚、可复盘。**
>
> **Claude Code 不得把未测试、未验收、未说明风险的任务包装成已完成。**

---

## 1. 文档定位

本文件是 `01-Standards/` 下的交付标准，也是 `01-Standards/` 的收口文件。

本文件汇总了 Tech Stack、Git、Security、Env Secrets、Dependency Review、Database、Testing、Logging Monitoring 八个标准，从"怎么交付"的角度统一验收出口。

### 本文件回答的问题

- 什么叫交付完成？代码写完算不算完成？
- 不同项目类型应该交付哪些内容？
- 文档任务、代码任务、MVP、商业项目各自怎么交付？
- 本地工具、Web 项目、数据库项目、AI/Agent 项目各自交付什么？
- 求职作品集怎么交付？客户接单项目怎么交付？
- 交付前必须检查什么？交付失败怎么处理？
- 如何归档已完成或已废弃的项目？

### 本文件不负责

- 具体代码实现 → `Coding_Workflow.md`
- 具体数据库迁移 → `Database_Standard.md`
- 具体测试代码 → `Testing_Standard.md`
- 具体部署脚本 → 运维/DevOps
- 具体客户合同 → `Business_Workflow.md`

## 2. 交付总原则

### 2.1 交付以结果为准，不以代码行数为准

写了 5000 行代码但功能不能正常使用 = 没有交付。写了 200 行代码但核心问题解决了 = 交付完成。交付衡量的是"用户能不能用"，不是"代码写了多少"。

### 2.2 交付必须有明确范围

这次交付了什么、不包含什么——必须在交付报告中写清楚。不能交付后客户说"我以为有这个功能"，你说"我没说包含"。

### 2.3 交付必须有验证结果

Build 跑了吗？Test 跑了吗？手动验收做了吗？每项的结果是什么？没有验证结果的交付 = 没有交付。

### 2.4 交付必须有风险说明

已知问题是什么？未覆盖的测试是什么？可能的失败场景是什么？不写风险不等于没有风险。

### 2.5 交付必须有回滚方案

如果这个交付有问题，怎么退回？`git revert`？数据库回滚？配置还原？没有回滚方案的交付是单向赌注。

### 2.6 交付必须有 Git 记录

每次交付必须有对应的 commit。Commit hash 是交付的唯一可验证证据。

### 2.7 交付必须有文档或说明

README、CLAUDE.md、.env.example、CHANGELOG——至少这些。让下一个接手的人能理解这是什么、怎么用。

### 2.8 交付不得包含真实密钥和客户隐私

`.env`、API Key、Token、数据库密码、客户数据——交付物中绝对不能出现。这是不可协商的硬底线。

### 2.9 商业交付必须可验收

客户能按照你给的步骤自己验证功能是否正常。验收标准必须在开发前就明确，而不是交付时才讨论。

### 2.10 Claude Code 任务必须输出交付报告

每次正式任务结束，无论大小，都必须有交付报告。报告是任务完成的唯一证明。

## 3. 交付完成定义

一个任务真正完成，必须满足以下 12 条：

| # | 条件 | 说明 |
|---|------|------|
| 1 | 需求范围已明确 | 知道要做什么、不做什么 |
| 2 | 修改范围已明确 | 知道改了哪些文件、没动哪些文件 |
| 3 | 实际修改已完成 | 代码/文档/配置已按方案完成 |
| 4 | 无关文件未被修改 | `git diff` 中只有方案列出的文件 |
| 5 | Build/Test 已执行或说明不适用 | 不能假装跑了测试 |
| 6 | 安全检查已执行 | 无密钥泄露、无客户数据暴露 |
| 7 | Git 状态已检查 | 开始前干净，结束后已提交 |
| 8 | Commit 已完成或说明原因 | 有 commit hash |
| 9 | 风险已说明 | 已知问题、未覆盖测试、潜在风险 |
| 10 | 回滚方式已说明 | 怎么退回去 |
| 11 | 交付报告已输出 | 完整的、真实的报告 |
| 12 | 下一步建议已给出但未擅自执行 | 建议是建议，不是继续做 |

### 交付 ≠ 完成 — 常见误解

| 误解 | 真相 |
|------|------|
| "代码写完了" = 完成 | 没有验证的代码不能叫完成 |
| "页面能打开" = 完成 | 能打开 ≠ 功能正确 |
| "Build 通过了" = 完成 | Build 只管编译，不管业务逻辑 |
| "客户没说问题" = 验收通过 | 客户没说不等于客户验收了 |
| "Claude Code 说完成了" = 完成 | AI 的判断需要交付报告来验证 |

## 4. 交付风险等级

### DLV0：低风险交付

**示例：** 文档修改、README 修改、Standards 修改、Workflow 修改、CLAUDE 规则修改、模板说明修改

**要求：** Git commit + 简化交付报告 + 说明 Build/Test 不适用 + 确认只修改了指定文件

### DLV1：普通交付

**示例：** 小功能修改、普通 UI 修改、普通 API 修改、非核心配置修改、小型 Bug 修复

**要求：** Build + 有测试则运行 + 手动验收 + 完整交付报告 + Git commit

### DLV2：高风险交付

**示例：** 数据库变更、登录/权限变更、依赖变更、导入导出功能、文件上传、部署配置、AI/Agent 工具调用、商业项目交付

**要求：** 明确授权 + Build/Test + 回归测试 + 安全检查 + 回滚方案 + 完整交付报告 + 必要时更新 README/CHANGELOG + 必要时记录 Decision Log

### DLV3：禁止自动交付

**示例：** 生产部署、生产数据库修改、自动 push 远程仓库、自动连接外部账号、自动发消息/支付/交易、未测试的商业交付、含真实密钥或客户隐私的交付包

**规则：** Claude Code 默认不得执行。必须停止并提示风险。必须拆成安全步骤。必须人工确认每一步。

## 5. 项目阶段与交付标准

| 阶段 | 必须交付 | 不应交付 |
|------|----------|----------|
| **Idea** | 问题说明、目标用户、初步价值判断、风险列表、下一步验证计划 | 完整系统、大型架构、复杂技术栈 |
| **Validation** | 用户访谈记录、痛点验证结果、竞品观察、是否继续判断、最小 MVP 范围 | — |
| **Prototype** | 可演示原型、核心流程说明、已知限制、手动验收步骤、下一版计划 | 完整产品、正式文档 |
| **MVP** | 可运行项目、README、CLAUDE.md、.env.example、核心功能说明、Build/Test 结果、手动验收记录、已知风险、回滚说明 | 完整权限系统、过度自动化、花哨 UI |
| **Beta** | 用户反馈记录、Bug 修复记录、CHANGELOG、核心流程回归测试、数据库变更说明、安全检查记录、交付报告 | — |
| **Release** | 稳定版本、README、CHANGELOG、版本号或 tag、Build/Test 结果、安全检查、部署说明、回滚方案、完整交付报告 | 真实密钥、客户数据、未脱敏内容 |
| **Maintenance** | Bug 修复说明、修改文件清单、回归测试结果、风险说明、版本记录、后续维护建议 | — |
| **Archive** | 项目状态说明、最后 commit hash、最后可运行方式、已知问题、不再维护原因、可复用资产总结 | — |

## 6. 标准交付物清单

### 所有正式项目至少应包含

| # | 交付物 | 说明 |
|---|--------|------|
| 1 | `README.md` | 项目是什么、怎么启动、怎么用 |
| 2 | `CLAUDE.md` | Claude Code 项目规则 |
| 3 | `CHANGELOG.md` | 版本变更记录 |
| 4 | `.env.example` | 环境变量模板（无真实值） |
| 5 | `package.json` 或等价配置 | 项目元信息和脚本 |
| 6 | `.gitignore` | Git 忽略规则 |
| 7 | 项目源码 | 按模板结构的完整代码 |
| 8 | 构建说明 | 怎么 Build |
| 9 | 启动说明 | 怎么启动 |
| 10 | 测试说明 | 怎么 Test |
| 11 | 交付报告 | 本次交付的完整记录 |

### 按需包含

- `docs/` — 项目文档
- `migrations/` — 数据库迁移文件
- `seed/` — 测试种子数据
- `scripts/` — 辅助脚本
- `deployment/` — 部署配置和说明
- `screenshots/` — 项目截图
- `demo-video` — 演示视频链接或文件
- API 文档 — Swagger 或 Markdown
- 数据库说明 — 表结构、关系、索引
- 用户手册 — 面向最终用户的操作说明
- 运维说明 — 面向运维人员的维护说明

### 禁止交付

- ❌ 真实 `.env`
- ❌ API Key / Token / 密码
- ❌ 真实客户数据
- ❌ 真实数据库文件
- ❌ 生产日志
- ❌ `node_modules/`
- ❌ 无关临时文件
- ❌ 未脱敏导出文件
- ❌ 浏览器 Cookie
- ❌ 外部账号凭证

## 7. README 交付标准

### README 必须说明（15 项）

| # | 内容 | 说明 |
|---|------|------|
| 1 | 项目名称 | 中英文 |
| 2 | 项目目标 | 一句话说清楚这个项目解决什么问题 |
| 3 | 目标用户 | 谁会使用 |
| 4 | 核心功能 | MVP 包含的功能列表 |
| 5 | 技术栈 | 前端、后端、数据库、关键依赖 |
| 6 | 目录结构 | 关键目录的用途 |
| 7 | 启动方式 | 从零到运行的完整步骤 |
| 8 | Build 方式 | 构建命令 |
| 9 | Test 方式 | 测试命令 |
| 10 | 环境变量说明 | 哪些变量、什么用途、怎么获取 |
| 11 | 数据库说明 | 数据库类型、初始化方式 |
| 12 | 已知限制 | 当前版本的边界 |
| 13 | 版本状态 | Prototype / MVP / Beta / Release |
| 14 | 安全提醒 | 注意事项 |
| 15 | 演示方式 | 截图、视频、在线链接 |

### 求职作品集额外要求

- 项目背景（为什么做这个项目）
- 技术亮点（技术选型的理由）
- 业务价值（解决了什么实际问题）
- 个人负责内容（你做了哪些部分）
- AI Coding 如何参与（Claude Code 在开发中的角色）
- 截图或演示链接
- 后续优化方向

### 商业项目额外要求

- 交付范围（包含什么）
- 不包含内容（明确排除，防止纠纷）
- 运行环境要求
- 客户需要配置的项目
- 维护注意事项
- 联系或交接说明

## 8. CLAUDE.md 交付标准

正式项目必须有项目级 `CLAUDE.md`，且必须包含：

| # | 内容 |
|---|------|
| 1 | 项目基本信息（名称、类型、目标、用户、阶段） |
| 2 | 项目边界（当前版本做什么、不做什么） |
| 3 | 技术栈（前端、后端、数据库、关键依赖） |
| 4 | 启动命令（开发、生产、前端、后端、数据库） |
| 5 | Build 命令 |
| 6 | Test 命令 |
| 7 | 数据库规则（类型、schema、migration、备份） |
| 8 | 环境变量规则（.env.example、禁止读取真实 .env） |
| 9 | Claude Code 可修改范围（哪些目录/文件可以改） |
| 10 | Claude Code 禁止事项（项目特有的禁止操作） |
| 11 | 项目特殊风险（本项目特有的高风险区域） |
| 12 | 交付验收标准（本项目怎么判断完成了） |

### 规则

- **项目 CLAUDE.md 必须继承 `CLAUDE_MASTER.md`。** 可以增加约束，不能放松底线。
- **不得在项目 CLAUDE.md 中放宽 `permission-policy.md` 的高风险限制。**
- **项目特殊规则必须写清楚。** 不能让 Claude Code 猜测。
- **不得让 Claude Code 在规则缺失的项目中自由发挥。**

## 9. CHANGELOG 交付标准

### 应记录

- 新增功能（`Added`）
- 修复问题（`Fixed`）
- 重构（`Changed`）
- 数据库变更
- 依赖变更（新增/删除/升级）
- 安全修复（`Security`）
- 破坏性变更（不向后兼容的修改）
- 已知问题（`Known Issues`）
- 交付版本号
- 用户反馈处理

### 推荐格式

```markdown
## [v0.2.0] - 2026-06-30

### Added
- Customer search by name and phone number
- Trial expiration warning banner

### Fixed
- Token refresh race condition on page reload

### Changed
- Refactored customer service into separate modules

### Security
- Added input validation on customer import endpoint

### Known Issues
- Search performance degrades with > 10,000 records
```

### 维护规则

1. **Release 前必须更新 CHANGELOG。**
2. **商业交付前必须更新 CHANGELOG。** 客户需要知道这个版本有什么。
3. **数据库变更必须记录。**
4. **依赖变更必须记录。**
5. **小型文档修改（typo、措辞调整）可不更新 CHANGELOG。**

## 10. Git 交付标准

### 交付前必须检查

| # | 检查项 |
|---|--------|
| 1 | `git status` 是否干净 |
| 2 | 修改文件是否符合交付范围 |
| 3 | 是否有范围外的无关文件 |
| 4 | 是否有真实 `.env` 出现在 staged 中 |
| 5 | 是否有 API Key / Token / 密码 |
| 6 | 是否有客户隐私数据 |
| 7 | 是否有真实数据库文件 |
| 8 | Commit message 是否清晰 |
| 9 | 是否需要 tag |
| 10 | 是否禁止 push（push 需单独授权） |

### 规则

- **所有正式交付必须有 Git commit。** Commit hash 写入交付报告。
- **商业交付版本建议有 tag。** 方便追溯和回滚。
- **求职作品集公开到 GitHub 前必须检查全部 Git 历史。** 确认无密钥、无客户数据。
- **Push 必须人工确认。** P3 操作，Claude Code 不得自动执行。
- **Force push / reset --hard / rebase 绝对不得自动执行。**

## 11. Build / Test 交付标准

> **说明：** 本章节定义交付摘要必填项。**测试细节以 `Testing_Standard.md` §24 为准。** 如果任务涉及代码、数据库、安全、Agent，应按 Testing_Standard.md 的完整测试报告项展开。二者不冲突：Delivery 摘要 + Testing 细项共同构成交付报告的测试部分。

交付报告必须写明以下测试相关内容：

| # | 内容 | 可能的值 |
|---|------|----------|
| 1 | 是否存在 Build 命令 | 是 / 否 |
| 2 | Build 是否执行 | 是 / 否 |
| 3 | Build 结果 | ✅ / ❌ / ⚠️ 未执行 / ➖ 不适用 |
| 4 | 是否存在 Test 命令 | 是 / 否 |
| 5 | Test 是否执行 | 是 / 否 |
| 6 | Test 结果 | ✅ / ❌ / ⚠️ 未执行 / ➖ 不适用 |
| 7 | 是否执行 Typecheck | 是 / 否 / 不适用 |
| 8 | 是否执行 Lint | 是 / 否 / 不适用 |
| 9 | 是否执行手动验收 | 是 / 否 |
| 10 | 是否执行回归测试 | 是 / 否 / 不适用 |
| 11 | 是否存在未覆盖风险 | 是 / 否，如有请说明 |

### 规则

- **Build 失败不得交付。** 先修复，再交付。
- **Test 失败不得交付。** 先修复，再交付。
- **未测试不得说成通过。** 没跑过的测试不允许填"通过"。
- **文档类任务可说明 Build/Test 不适用。**
- **没有测试命令必须在交付报告中说明风险 ⚠️。**
- **商业交付必须至少有手动验收记录。**

## 12. 安全交付标准

### 交付前必须逐项检查

| # | 检查项 |
|---|--------|
| 1 | 没有真实 `.env` |
| 2 | 没有 API Key |
| 3 | 没有 Token |
| 4 | 没有数据库密码 |
| 5 | 没有真实 `DATABASE_URL` |
| 6 | 没有客户隐私数据 |
| 7 | 没有真实日志文件 |
| 8 | 没有真实数据库文件 |
| 9 | 没有生产配置 |
| 10 | 没有外部账号凭证 |
| 11 | API 不返回敏感字段（密码哈希、Token、内部路径） |
| 12 | 日志不泄露敏感信息 |
| 13 | 文件上传有类型和大小限制 |
| 14 | 导入导出有权限边界 |
| 15 | Agent/自动化不越权操作 |

### 规则

- **发现安全风险不得交付。** 必须先脱敏或移除。
- **密钥泄露必须立即更换。** 不能"下次再说"。
- **交付报告不得暴露密钥。** 引用变量名，不引用变量值。
- **安全检查是交付前的最后一道关。** 不过关 = 不交付。

## 13. 环境变量交付标准

### 交付必须包含

- ✅ `.env.example`（完整变量模板，只有占位符）
- ✅ 环境变量说明（每个变量的用途）
- ✅ 必填变量列表
- ✅ 可选变量列表
- ✅ 示例格式（用户知道填什么格式的值）
- ✅ 缺失变量影响说明（哪个功能会不可用）

### 不得交付

- ❌ 真实 `.env`
- ❌ 生产密钥
- ❌ 客户密钥
- ❌ 云服务密钥
- ❌ 支付密钥
- ❌ AI API Key 真实值

### 规则

1. **用户或客户手动配置真实密钥。** Claude Code 不代填。
2. **Claude Code 不得读取真实 `.env`。** 只读 `.env.example`。
3. **README 必须说明环境变量的配置方式。**
4. **交付包（zip、tar、部署包）不得包含真实 `.env`。**
5. **Docker / CI/CD 配置示例不得包含真实 secrets。**

## 14. 数据库交付标准

数据库相关项目必须交付：

| # | 内容 |
|---|------|
| 1 | 数据库类型说明（PostgreSQL / MySQL / SQLite） |
| 2 | Schema 说明（表结构、关系、关键字段） |
| 3 | Migration 说明（如何生成、如何执行、如何回滚） |
| 4 | Seed 说明（测试数据的内容和用途） |

## 23. 验收流程标准

### 标准验收流程

```
确认交付范围（对照合同/需求文档）
    ↓
确认运行环境（客户环境 vs 开发环境）
    ↓
交付文件（代码、文档、配置）
    ↓
按 README 启动（一条命令能启动）
    ↓
执行核心流程（最重要的 2-3 个用户操作路径）
    ↓
执行异常流程（错误输入、边界情况）
    ↓
检查数据结果（数据是否正确保存、查询、展示）
    ↓
检查错误日志（无隐藏的异常）
    ↓
确认已知限制（交付报告中声明的限制是否属实）
    ↓
记录验收结果
    ↓
确认是否通过
```

### 验收结果

| 结果 | 含义 | 处理 |
|------|------|------|
| ✅ 通过 | 所有核心功能正常，已知限制已说明 | 可交付 |
| ⚠️ 部分通过 | 核心功能可用但存在非阻塞问题 | 说明哪些未通过 + 是否影响使用 + 是否进入下一轮 |
| ❌ 未通过 | 核心功能不可用或存在阻塞问题 | 不得交付，修复后重新验收 |

| # | 内容 |
|---|------|
| 1 | Bug 描述（什么现象） |
| 2 | 复现步骤（从哪一步开始、做了什么、看到了什么） |

| 10 | 是否更新交付报告 |

### Bug 严重程度

| 级别 | 定义 | 处理 |
|------|------|------|
| **B0** | 阻塞核心流程，系统无法使用 | 不解决不交付 |

| **B2** | 影响普通功能，有替代路径 | 可视情况交付，但必须说明 |
| **B3** | 轻微问题或文案问题 | 可进入后续优化 |

### 规则

- **B0/B1 未解决不得正式交付。**
- **B2 可视项目情况交付但必须在报告中说明。**
- **B3 可进入后续迭代。**
- **修复后必须回归测试。** 确认修复有效且未引入新问题。

## 25. 回滚与恢复交付标准

### 交付报告必须说明回滚方式

| 回滚类型 | 方式 | 说明 |
|----------|------|------|
| Git 回滚 | `git revert <hash>` | 代码回到修改前状态 |
| 配置回滚 | 恢复原配置文件 | 改了 nginx、docker、env 等 |
| 数据库回滚 | 恢复备份或执行 down migration | 数据回到变更前 |
| 依赖回滚 | 重新安装旧版本 | `npm install package@old-version` |
| 部署回滚 | 重新部署上一版本 | 代码 + 配置 + 数据库联动 |
| 文档回滚 | `git revert` 或手动恢复 | 文档回滚最安全 |

### 必须说明

| # | 内容 |
|---|------|
| 1 | 回滚目标（回到哪个版本/commit/状态） |
| 2 | 回滚命令或步骤（具体可执行的操作） |
| 3 | 是否影响数据 |
| 4 | 是否需要备份 |
| 5 | 是否需要停机 |
| 6 | 谁执行（人工还是脚本） |
| 7 | 回滚本身的风险是什么 |

### 禁止

- ❌ 没有回滚方案就做高风险交付
- ❌ 把"删除数据库"当成回滚方案
- ❌ 把"重新做一遍"当成回滚方案
- ❌ 让 Claude Code 自动回滚生产环境

## 31. 常见交付错误与处理

### 31.1 代码写完但不能启动

**处理：** 不得交付 → 检查启动命令 → 检查环境变量 → 检查依赖 → 检查数据库连接 → 修复后重新验收

### 31.2 Build 失败

**处理：** 不得交付 → 分析错误 → 最小范围修复 → 最多自动修复 3 轮 → 失败后停止询问用户

### 31.3 缺少 README

**处理：** 补 README → 说明启动方式 → 说明配置 → 说明已知限制 → 再交付

### 31.4 交付包含真实密钥

**处理：** 立即停止交付 → 移除密钥 → 判断是否已泄露 → 必要时更换密钥 → 检查 Git 历史 → 记录安全事件

### 31.5 客户说"不符合预期"

**处理：** 回到验收标准 → 判断是否在约定范围内 → 范围内则修复 → 范围外则进入变更需求（新报价或下一期） → 不无限免费返工

### 31.6 Claude Code 漏写交付报告

**处理：** 不算完成 → 立即补交付报告 → 明确 Build/Test/Git/风险 → 不允许用一句"已完成"糊弄

## 附录 A：v3.2 Evidence State 与完成判断

### A.1 证据状态链

交付报告应在适用范围内区分以下状态，不得把其中任一状态自动等同为最终完成：

```text
Claim
→ Corroborating Evidence
→ Self-Verified
→ Independently Verified（如被触发）
→ Completion Decision
→ Production Readiness Decision（如适用）
```

允许的证据结论包括：`PASS`、`PASS WITH OBSERVATIONS`、`INCONCLUSIVE`、`FAIL`、`NOT COMPLETED`。`INCONCLUSIVE` 必须保留证据缺口，不得自动改写为 `PASS` 或 `FAIL`。

### A.2 验证状态与独立性引用

每个 Work Package 必须完成 Self-Verify。Independent Audit 是否触发，依照 `Agent_Collaboration_Standard.md` 的角色、责任与独立性规则判断；本标准只要求交付报告记录该判断及其对完成结论的影响，不重复定义审计流程。

### A.3 Persistent Evidence Bundle 触发规则

Persistent Evidence Bundle 不是所有 Work Package 的默认交付物。仅在运行时、外部边界、难以事后复核或治理要求触发时要求生成；普通文档修改、小范围静态调整或其他可直接复核的低复杂度任务，记录适用的验证摘要即可。

仅当验证难以事后复现、依赖运行时或包含外部边界时，才要求按场景生成 Evidence Bundle，例如：

- Browser E2E；
- Provider 或外部网络请求；
- 数据库写入及读回；
- Hook 生命周期触发；
- 环境依赖导致的运行验证；
- 其他经风险判断需要独立复核的运行结果。

触发时至少保留原始命令、原始输出、运行环境、时间、关键状态、失败历史及可供 Auditor 复核的 Evidence IDs；不得在报告中用摘要替代原始证据的存在性说明。

### A.4 Completion Decision 与 Production Readiness Decision

**Completion Decision** 判断当前 Work Package 或交付范围是否已经满足其约定的完成条件。它必须基于范围、适用验证、风险、证据状态和未完成项形成；由负责该 Work Package 的 Main Agent 提出并确认，必要时由用户或被触发的 Independent Auditor 根据其职责进行确认。Delivery Report 是该 Decision 的记录载体，但报告本身不是未经证据支持的完成授权。

Completion Decision 不等于 Commit。Commit 仍受独立的 Commit-only Authorization 约束；未获得该授权时，可以形成并记录 Completion Decision，但不得因完成判断自动执行 commit。反之，commit 也不得自动推导 Completion Decision。

**Production Readiness Decision** 判断是否具备面向生产环境、真实用户、真实客户数据或正式部署的条件。仅当交付目标涉及生产、正式部署、真实用户或真实客户数据时适用；纯文档、开发环境或内部非生产交付可以标记为不适用。

该 Decision 必须由具备相应治理责任的 Main Agent 提出，并由用户或明确指定的发布/生产责任人确认；涉及高风险场景时还必须满足适用的独立审查和 Protected Action 要求。测试通过、Delivery Report 已完成、Completion Decision 已形成或 commit 已创建，均不得自动推导 Production Readiness。

### A.5 Decision Log 边界

`decision-log.md` 只记录实际发生的治理、范围、架构、风险或状态决策，不承担通用 Evidence State 或 Finding Closure 模板职责。通用格式应由本标准和交付报告模板定义；只有真实发生的 v3.2 决策才新增日志记录，并保留历史记录。
