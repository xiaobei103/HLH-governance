# Database_Standard.md：HLH AI 软件工程数据库标准

> 本文件定义 HLH AI Software Engineering Workflow v3.0 的数据库标准。
>
> **所有正式项目涉及数据库时，必须遵守本文件。**
>
> **数据库操作必须优先保护数据安全、可迁移性、可回滚性和长期维护性。**
>
> **Claude Code 不得为了解决报错自动删除数据库、清空数据或修改生产数据库。**

---

## 1. 文档定位

本文件是 `01-Standards/` 下的数据库标准。

### 本文件回答的问题

- 什么项目应该用 PostgreSQL？MySQL？SQLite？
- 数据库 schema 应该如何设计？
- Prisma migration 应该如何安全使用？
- 什么时候允许修改数据库结构？
- 什么时候必须备份？什么时候必须停止并询问用户？
- 测试数据库和生产数据库如何隔离？
- 数据导入导出如何处理？
- 数据库文件是否可以进入 Git？
- Claude Code 能不能自动执行数据库命令？
- 数据库出错后如何安全处理，而不是删库重来？

### 本文件不负责

- 具体业务表结构设计 → `Project_Workflow.md`
- 具体 SQL 代码实现 → `Coding_Workflow.md`
- 具体部署脚本 → `Delivery_Standard.md`
- 具体云数据库购买 → 运维/DevOps 决策
- 具体客户数据合规合同 → 法律咨询

## 2. 数据库总原则

### 2.1 数据安全优先于开发速度

功能可以推迟上线，数据丢失不可接受。任何涉及真实数据的操作，宁可慢一步，不可错一步。

### 2.2 真实数据优先于代码便利

不能为了"方便 Debug"而把真实数据库复制到本地随便操作。不能为了"方便测试"而在生产库上跑实验查询。

### 2.3 数据库变更必须可追踪

每次 schema 变更、migration、批量数据修改，都必须有记录。谁在什么时候改了什么、为什么改。

### 2.4 数据库变更必须可回滚

每个 migration 都应该有对应的回滚方案。没有回滚方案的变更 = 不可逆的赌博。

### 2.5 生产数据库默认最高风险（DB3）

任何涉及生产数据库的写操作、结构变更、数据修改都是 DB3 级别。必须人工操作或单独授权。

### 2.6 测试环境不得连接生产数据库

测试可能产生脏数据、可能清空表、可能高负载、可能误操作。测试和生产必须物理隔离。

### 2.7 SQLite Demo 不等于正式多人系统

SQLite 适合单机和本地验证。多人并发、SaaS、商业交付场景下不应使用 SQLite。不要把 Demo 的 SQLite 当成"数据库已经做好了"。

### 2.8 Schema 变更必须先分析影响范围

新增字段？删除字段？修改类型？重命名字段？——每项操作都要分析：影响哪些 API、哪些前端页面、哪些已有数据、哪些测试。

### 2.9 Migration 不能为了解决报错乱删乱改

Migration 失败时，正确的做法是分析错误、修复 migration，而不是删除 migration 文件、清空数据库、或 `prisma db push --force`。

### 2.10 Claude Code 不得自动删除数据库或清空数据

数据库删除是不可逆操作。Claude Code 默认不得执行任何 DROP、TRUNCATE、无条件 DELETE。这是 DB3 硬规则。

## 3. 数据库选择标准

### 3.1 PostgreSQL

**适用：** 长期 AI 产品、AI Operating System、Agent 系统、SaaS、多模块系统、需要复杂查询或向量扩展（pgvector）的项目

**优势：** 功能最强、扩展性最好、支持复杂数据关系、适合 AI/Agent 数据场景、pgvector 可用于 AI 向量检索

**限制：** 配置和运维复杂度高于 SQLite、对普通小客户解释成本高于 MySQL、本地开发环境需认真管理

**默认结论：** 长期 AI 产品优先 PostgreSQL。

### 3.2 MySQL

**适用：** 国内普通商用项目、CRM、管理后台、企业内部系统、外包接单、客户已有 MySQL 环境

**优势：** 中国普及率极高、客户和运维人员更熟悉、国内云服务支持好、适合普通商业交付

**限制：** AI/向量扩展不如 PostgreSQL 方便、复杂 AI 数据场景不一定最优

**默认结论：** 国内普通商用系统优先 MySQL。

### 3.3 SQLite

**适用：** 本地工具、快速 MVP、单机试用版、小型个人项目、小规模原型验证

**优势：** 零部署、极简、本地运行方便、适合快速验证

**限制：** 不适合多人并发、不适合正式 SaaS、不适合复杂权限系统、数据文件易误删、备份和迁移需额外小心

**默认结论：** SQLite 只适合本地工具和 MVP 验证，**不得直接作为正式多人商业系统数据库。**

## 4. 数据库风险等级

### DB0：低风险

**示例：** 修改数据库说明文档、修改 `.env.example` 中的 `DATABASE_URL` 占位符、新增测试数据说明、查看 schema 文件（只读）

**规则：** 按 R0 文档任务处理。仍需 Git 记录和交付报告。

### DB1：中风险

**示例：** 新增非关键查询（SELECT）、新增只读 API、新增测试 seed（仅结构和假数据）、修改开发环境数据库说明、建议增加索引（不执行生产变更）

**规则：** 必须说明影响范围。必须 Build/Test。必须确认不涉及真实数据。

### DB2：高风险

**示例：** 修改 schema、新增/执行 migration、修改数据导入导出、批量 UPDATE、修改 ORM 配置、修改数据库连接变量、修改备份策略

**规则：** 必须等待明确授权。必须说明每项风险和缓解措施。必须说明回滚方案。**涉及真实数据必须先备份。** 必须写入交付报告。

### DB3：禁止自动执行

**示例：** 删除数据库（DROP DATABASE）、清空数据表（TRUNCATE/无条件 DELETE）、删除生产数据、删除真实 SQLite `.db` 文件、为解决报错删除 migration、为解决报错清空表、连接生产数据库执行写操作、未备份前批量修改真实数据

**规则：** Claude Code 默认不得执行。必须强烈提示数据丢失风险。必须建议更安全的替代方案。需要用户单独授权，且优先由用户手动操作。

## 5. Schema 设计原则

### 设计规则

1. **表名必须清晰表达业务含义。** `customers` 不是 `t_cust`，`orders` 不是 `data1`。
2. **字段名必须清晰表达数据含义。** `phone_number` 不是 `col_3`，`created_at` 不是 `d1`。
3. **主键必须明确。** 每个表都应有主键。优先使用 `id`（UUID 或自增整数，按需选择）。
4. **必要字段必须设置非空约束（NOT NULL）。** 不应该为 null 的字段，从 schema 层面就禁止 null。
5. **枚举字段必须限制范围。** 状态字段、类型字段用枚举或 CHECK 约束，接受非法值。
6. **时间字段应统一命名。** `created_at`、`updated_at`、`deleted_at` 全项目一致。
7. **重要业务数据应有 `created_at` 和 `updated_at`。** 无时间戳的数据 = 不可审计的数据。
8. **删除策略必须明确。** 是硬删除还是软删除？从 schema 设计阶段就确定。
9. **外键关系必须谨慎设计。** 级联删除（CASCADE）是危险的——明确你是否真的需要。
10. **不为了快速开发随便往 JSON 字段塞数据。** JSON 列没有类型安全、不可查询、不可索引——只有明确需要灵活 schema 的场景才使用。

### 推荐字段命名

```
id            — 主键
name          — 名称
title         — 标题
description   — 描述
status        — 状态（枚举）
type          — 类型（枚举）
source        — 来源
priority      — 优先级
note          — 备注
created_at    — 创建时间
updated_at    — 更新时间
deleted_at    — 软删除时间
created_by    — 创建人
```

### Schema 设计禁止

- ❌ 不要过度设计（MVP 只有 5 个功能，不需要 20 张表）
- ❌ 不要为了"未来可能需要"添加大量空字段
- ❌ 不要把所有内容塞到一个大宽表里
- ❌ 不要把数据库当临时文本文件乱用
- ❌ 不要用 `TEXT` 存储所有字段来"省事"

## 6. Prisma 使用标准

Prisma 是当前 TypeScript 项目的默认 ORM。

### 支持的数据库

PostgreSQL、MySQL、SQLite

### 规则

1. **`prisma/schema.prisma` 必须进入 Git。** 这是数据库结构的唯一真源（single source of truth）。
2. **Prisma migration 文件应进入 Git。** `prisma/migrations/` 目录属于版本管理。
3. **`.env` 中的真实 `DATABASE_URL` 不进入 Git。** 见 `Env_Secrets_Standard.md`。
4. **`.env.example` 应给出 `DATABASE_URL` 占位符示例。**
5. **修改 schema 前必须分析影响范围。** 见第 7 节。
6. **Migration 属于 DB2 高风险。** 执行前必须确认和备份。
7. **不得为了解决报错随意删除 `prisma/migrations/` 目录中的文件。**
8. **不得为了解决报错重置真实数据库（`prisma migrate reset`）。**
9. **开发环境可生成 migration，但每次生成后必须说明变更内容。**
10. **生产 migration 必须有备份和回滚方案。**

### 禁止

- ❌ 直接让 Claude Code 自动执行生产 `prisma migrate deploy`
- ❌ 乱用 `prisma db push` 覆盖正式数据库结构（`db push` 不生成 migration 文件，不可追溯）
- ❌ Migration 失败后清空数据库重来
- ❌ 删除 migration 历史来掩盖问题
- ❌ 用 `--force` 标志跳过确认

## 7. Migration 标准流程

```
提出 schema 变更需求（为什么要改表结构？）
    ↓
说明业务原因（这个变更服务什么功能？）
    ↓
分析影响范围（涉及哪些表？影响哪些 API？影响哪些前端页面？）
    ↓
确认数据库环境（开发？测试？生产？——这个操作针对哪个环境？）
    ↓
确认是否涉及真实数据（已有数据会不会被影响？）
    ↓
设计迁移方案（新增字段？修改类型？删除字段？默认值怎么处理？）
    ↓
设计回滚方案（如果 migration 有问题，怎么回退？）
    ↓
必要时备份（涉及真实数据 = 必须先备份）
    ↓
生成 migration（`prisma migrate dev --name <description>`）
    ↓
在开发环境测试（先在本地跑，确认 migration 可执行且应用可运行）
    ↓
运行 Build / Test（确认代码与 schema 一致）
    ↓
更新文档（README、CHANGELOG、API 文档）
    ↓
写入交付报告（说明 migration 内容和结果）
```

### 每次 Migration 必须说明

| # | 说明项 |
|---|--------|
| 1 | 修改了哪些表 |
| 2 | 新增了哪些字段 |
| 3 | 修改了哪些字段类型 |
| 4 | 删除了哪些字段 |
| 5 | 新增了什么约束（NOT NULL、UNIQUE、FOREIGN KEY） |
| 6 | 是否影响已有数据 |
| 7 | 是否需要设置默认值 |
| 8 | 是否需要数据迁移（如拆分字段、格式转换） |
| 9 | 是否影响 API 返回格式 |
| 10 | 是否影响前端展示 |
| 11 | 如何回滚 |

## 8. Seed 数据标准

Seed 数据用于初始化开发或测试环境的基础数据。

### 允许的 Seed 内容

- 脱敏样例数据（假姓名、假电话、假公司）
- 测试账号（`test@example.com`）
- 测试分类/标签
- 本地演示数据
- 系统预设的基础数据（国家列表、货币列表等不敏感数据）

### 禁止的 Seed 内容

- ❌ 真实客户数据
- ❌ 真实手机号、微信号、邮箱
- ❌ 真实医疗信息、财务信息
- ❌ 真实成交记录
- ❌ 真实账号密码
- ❌ 生产数据的直接复制品

### 规则

1. **Seed 脚本必须清楚说明用途。** 这是初始化数据还是演示数据？
2. **Seed 默认只用于开发和测试环境。** 不在生产环境跑 seed，除非 seed 是系统必需的初始数据且经确认。
3. **不得在生产环境随意运行 seed。** `prisma db seed` 在生产环境执行前必须确认。
4. **Seed 数据必须可重复执行（幂等）或说明限制。** 跑两次不会产生重复脏数据。
5. **Seed 运行前必须确认目标环境。** 在哪个数据库上跑？开发还是测试？
6. **Seed 失败不得通过清空数据库解决。** 检查数据冲突原因，修复 seed，再重试。
7. **Seed 脚本应进入 Git，真实数据不得进入 Git。**
8. **Seed 变更必须写入交付报告。**

## 9. 数据导入标准

### 导入类型

Excel 导入、CSV 导入、JSON 导入、外部系统数据导入、客户历史数据导入

### 导入前必须确认

| # | 确认项 |
|---|--------|
| 1 | 数据来源（从哪里来的数据） |
| 2 | 数据字段（有哪些列、各是什么含义） |
| 3 | 数据量（多少行，是否需要分批处理） |
| 4 | 是否包含敏感信息（姓名、手机号、身份证等） |
| 5 | 是否需要脱敏后再导入 |
| 6 | 是否需要备份当前数据 |
| 7 | 是否允许覆盖已有数据（重复键怎么处理） |
| 8 | 是否允许新增重复数据 |
| 9 | 失败后如何处理（全部回滚？部分导入？） |
| 10 | 是否需要生成导入报告 |

### 导入规则

- 必须校验字段结构（列数、列名、数据类型）
- 必须校验数据类型（字符串、数字、日期）
- 必须处理空值（哪些允许空、哪些必须有值）
- 必须处理重复数据（按什么键判断重复）
- 必须记录导入成功和失败数量
- **不得未经确认覆盖已有数据**
- **不得把客户导入文件（含真实数据）提交 Git**
- 导入真实客户数据属于 DB2 高风险

## 10. 数据导出标准

### 导出类型

Excel 导出、CSV 导出、JSON 导出、备份导出、客户请求的数据导出

### 导出前必须确认

| # | 确认项 |
|---|--------|
| 1 | 谁可以导出（权限控制） |
| 2 | 导出哪些字段（是否过滤了敏感字段） |
| 3 | 是否包含敏感信息（手机号、身份证、医疗信息） |
| 4 | 是否需要脱敏后再导出 |
| 5 | 导出文件保存在哪里（不会进入 Git） |
| 6 | 导出文件是否会意外进入 Git |
| 7 | 导出文件是否需要加密 |
| 8 | 导出后如何清理（临时文件是否删除） |
| 9 | 是否需要操作日志（谁在什么时候导出了什么） |
| 10 | 是否符合交付范围（客户要的数据 vs 不能给的数据） |

### 导出规则

- **客户隐私字段默认不导出。** 手机号、身份证、医疗信息——除非明确授权。
- **导出敏感数据必须确认权限。** 不是所有用户都能导出所有数据。
- **导出文件默认不进入 Git。** 确认 `.gitignore` 覆盖了导出目录。
- **导出文件不得长期存放在可公开访问的位置。**
- **商业项目的导出功能必须有权限控制。**
- **导出行为应写入操作日志。**

## 11. 备份标准

### 必须备份的场景

- 执行 migration 前（涉及真实数据时）
- 批量导入前
- 批量更新前
- 批量删除前
- 数据修复前
- 大版本升级前
- 商业交付前
- 生产部署前

### 备份必须说明

| # | 说明项 |
|---|--------|
| 1 | 备份对象（整个数据库还是特定表） |
| 2 | 备份时间（什么时候做的备份） |
| 3 | 备份位置（备份文件存在哪里） |
| 4 | 备份方式（`pg_dump`？`mysqldump`？复制 `.db` 文件？） |
| 5 | 是否已验证可恢复（备份不做恢复测试 = 可能备份是坏的） |
| 6 | 谁负责保管 |
| 7 | 是否包含敏感数据 |
| 8 | 是否需要加密 |
| 9 | 保留期限（什么时候可以删除这个备份） |
| 10 | 是否进入 Git（默认不进） |

### 规则

- **备份不是 Git 的替代品。** Git 管代码，备份管数据。两者职责不同。
- **Git 不是数据库备份。** 不要把 `.sql` dump 文件提交到 Git 作为"备份"。
- **真实备份默认不进入 Git。** 备份文件通常大且包含敏感数据。
- **备份文件必须避免泄露。** 不要放在公开目录、不要通过聊天工具发送。
- **备份后必须确认可恢复性。** 没有经过恢复测试的备份不能称为备份。

## 12. 回滚标准

数据库回滚比代码回滚更危险。代码的 `git revert` 是秒级的。数据的回滚可能需要停机、可能丢失新数据、可能影响业务。

### 回滚前必须确认

| # | 确认项 |
|---|--------|
| 1 | 回滚原因（为什么要回滚） |
| 2 | 回滚目标版本（回到哪个 migration 或备份点） |
| 3 | 是否影响代码（代码是否依赖新 schema） |
| 4 | 是否影响已有数据（回滚后新写入的数据会不会丢失） |
| 5 | 是否有可用备份 |
| 6 | 是否需要停机 |
| 7 | 是否会丢失新数据（备份之后写入的数据怎么处理） |
| 8 | 是否需要用户确认 |
| 9 | 是否有替代修复方案（前进修复 vs 回滚） |

### 禁止

- ❌ 为了"快"直接删除数据库
- ❌ 为了回滚直接清空表
- ❌ 没有备份就回滚真实数据
- ❌ 不确认环境就执行回滚（在开发环境测试的 migration 和生产环境不一样）
- ❌ Claude Code 自动回滚生产数据库

### 规则

- 代码可以 `git revert`，数据不能随便 revert。
- Migration 回滚必须结合备份。
- **数据修复优先小范围、可验证的方案。** 不要为了修 1 行数据去跑 1 万行的脚本。
- 回滚过程必须记录到交付报告。

## 13. 测试数据库标准

### 规则

1. **测试不得连接生产数据库。** 物理隔离——不同的连接串、不同的服务器/文件。
2. **测试不得使用真实客户数据。** 用 seed 的假数据。
3. **测试数据库应可随时重建。** 跑一个命令就能从零恢复到测试状态。
4. **测试数据应为脱敏或虚构数据。** 张三、李四、13800000000。
5. **E2E 测试应使用专用测试账号。** 不用真实用户账号跑自动化。
6. **测试失败不得通过修改生产数据来"解决"。**
7. **测试数据库配置应与生产完全隔离。** `.env.test` 独立于 `.env` 和 `.env.production`。
8. **测试完成后可清理测试数据，但不得误删其他环境的数据库。**
9. **CI 测试应使用独立测试数据库。** 每个 CI run 使用新建或重置的数据库。
10. **测试数据库连接变量必须清晰命名。** 推荐：`TEST_DATABASE_URL` 或 `DATABASE_URL_TEST`。

## 14. 生产数据库标准

生产数据库是最高风险区域（DB3）。

### Claude Code 禁止自动执行

- 连接生产数据库
- 执行生产 migration
- 删除生产数据
- 清空生产表
- 修改生产数据库连接串
- 导出生产客户数据
- 导入未经验证的数据到生产库
- 重置生产数据库
- 执行任何未审查的 SQL 语句
- 为了修错直接操作生产数据

### 生产数据库操作前必须具备（10 项全部满足）

| # | 条件 |
|---|------|
| 1 | 明确的操作目的（为什么要操作生产库） |
| 2 | 用户明确授权（不是随口的"好"，是"确认执行生产数据库操作"） |
| 3 | 当前有效的备份（不是上周的，是操作前刚做的） |
| 4 | 已测试的回滚方案 |
| 5 | 合适的操作窗口（低流量时段） |
| 6 | 影响范围说明（影响哪些功能、哪些用户） |
| 7 | 已通过开发/测试环境验证 |
| 8 | 操作过程记录（每一步都有日志） |
| 9 | 失败处理方案（如果操作失败，应急步骤是什么） |
| 10 | 交付报告 |

## 15. SQLite 特别规则

SQLite 的数据库就是一个文件，很容易被误删、误提交、误覆盖。

### 规则

1. **SQLite 真实数据库文件默认不进入 Git。** `.gitignore` 中必须有 `*.sqlite`、`*.sqlite3`、`data.db`。
2. **如需提交测试 SQLite 文件，必须明确声明是脱敏样例数据。** 在 commit message 中说明。
3. **试用版或本地工具必须在 README 中说明数据文件的位置。**
4. **本地工具必须在 README 中说明备份方式。** 告诉用户怎么保护自己的数据。
5. **不得为了解决报错直接删除 `data.db`。** 这是 DB3 禁止操作。
6. **删除 SQLite 文件等于删除整个数据库，属于 DB3 高风险。**
7. **商业交付使用 SQLite 时，必须在交付文档中说明其限制。** 不适合多人、不适合高并发。
8. **多人使用场景不应默认使用 SQLite。** 任何超过 1 个并发用户的场景，评估是否需要升级。
9. **SQLite 升级到 MySQL/PostgreSQL 必须走正式的迁移方案。** 不是简单换连接串。

## 16. MySQL 特别规则

MySQL 适合国内普通商用项目。

### 规则

1. **MySQL 连接信息必须放在 `.env`，不进入 Git。**
2. **不得把 MySQL 密码写进代码任何位置。**
3. **字符集应优先使用 `utf8mb4`。** `utf8` 在 MySQL 中不支持完整的 Unicode（emoji 等）。
4. **时间字段应统一为 `DATETIME` 或 `TIMESTAMP`，全项目一致。**
5. **生产环境必须定期备份。** 至少每次 migration 前备份。
6. **Migration 前必须确认当前连接的是哪个环境。** 开发库还是生产库？
7. **客户已有 MySQL 环境时，必须先确认版本和字符集。**
8. **导入导出必须注意编码。** MySQL 的编码问题是中国开发者最常见的坑之一。
9. **商业项目交付时必须说明 MySQL 部署和备份方式。**
10. **MySQL 相关变更必须写入交付报告。**

---

## 17. PostgreSQL 特别规则

PostgreSQL 适合长期 AI 产品。

### 规则

1. **PostgreSQL 连接信息必须放在 `.env`，不进入 Git。**
2. **不得把 PostgreSQL 密码写进代码任何位置。**
3. **涉及 pgvector 前必须确认是否真的需要向量检索。** 不是所有 AI 项目都需要向量数据库。
4. **复杂查询应考虑索引。** 用 `EXPLAIN ANALYZE` 确认查询计划后再加索引。
5. **Schema 变更必须通过 migration，不能手动改表。**
6. **生产环境必须定期备份。** `pg_dump` 是基本操作。
7. **AI 数据和业务数据边界必须清晰。** Agent 产生的数据 vs 用户产生的数据，分 schema 或分表管理。
8. **向量数据不得混入未经授权的客户隐私。**
9. **PostgreSQL 扩展安装（如 `CREATE EXTENSION`）属于 DB2 高风险。** 不是所有扩展都安全或必要。
10. **PostgreSQL 相关变更必须写入交付报告。**

## 18. 索引与性能规则

索引用于提升查询性能，但不是免费的——每个索引都会拖慢写入速度并占用磁盘空间。

### 适合建立索引的字段

- 高频查询的 WHERE 条件字段
- 外键字段（JOIN 的关联键）
- 搜索字段（姓名、手机号、订单号）
- 排序字段（`ORDER BY created_at DESC`）
- 状态字段 + 时间字段的组合
- 唯一约束自动创建索引

### 谨慎建立索引的字段

- 低选择性字段（如只有 3 种值的 `status` 字段，索引收益低）
- 大文本字段（TEXT 类——考虑前缀索引或全文搜索）
- 很少被查询的字段（索引维护成本 > 查询收益）
- 频繁写入但很少读取的字段（索引会拖慢每次写入）

### 规则

1. **索引必须服务真实的、可测量的查询需求。** 不猜测，用 `EXPLAIN` 验证。
2. **不为了"看起来专业"乱加索引。**
3. **新增索引属于数据库结构变更（DB2）。** 需要 migration 和说明。
4. **大表加索引可能锁表、耗时巨大。** 生产环境操作前评估影响。
5. **索引变更必须写入交付报告。**

## 19. 删除策略

删除数据有两种方式，各有利弊。

### 19.1 硬删除（Hard Delete）

直接从数据库中物理删除记录。

**适用：** 测试数据、临时数据、明确不需要保留且不涉及审计的数据

**风险：** 不可恢复、容易误删、不留审计痕迹

### 19.2 软删除（Soft Delete）

通过 `deleted_at` 字段标记删除，数据仍保留在表中。

**适用：** 客户数据、业务记录、订单、跟进记录、任何需要审计的数据

**优势：** 可恢复、可审计、误删可撤销

### 规则

1. **重要业务数据优先使用软删除。** 一旦发现误删，能立刻恢复。
2. **删除功能必须有确认交互。** 不能点一下就删。
3. **批量删除属于 DB2 高风险。** 必须确认删除范围和备份状态。
4. **删除客户数据必须有权限控制。** 不是所有用户都能执行删除。
5. **删除行为应进入操作日志或审计记录。** 谁在什么时候删了什么。

## 20. 数据权限与隔离

涉及多用户或多租户时，数据隔离是基本安全要求。

### 必须明确回答

| # | 问题 |
|---|------|
| 1 | 谁可以看哪些数据？（行级权限） |
| 2 | 谁可以修改哪些数据？ |
| 3 | 谁可以删除哪些数据？ |
| 4 | 谁可以导出哪些数据？ |
| 5 | 是否需要租户隔离？（不同组织/客户的数据完全隔离） |
| 6 | 是否需要组织内角色权限？（管理员 vs 普通成员） |
| 7 | 是否需要操作日志？（谁在什么时候做了什么） |
| 8 | 是否需要审计记录？ |
| 9 | 是否存在越权访问风险？（用户 A 能否通过修改 URL 参数看到用户 B 的数据） |

### 规则

- **不允许只靠前端隐藏按钮做权限控制。** 后端每一次查询都必须校验数据归属。
- **后端查询必须基于登录用户的身份过滤数据。** `WHERE user_id = current_user.id`。
- **导出和删除操作必须特别校验权限。** 这两种操作对数据影响最大。
- **多租户数据不得互相泄露。** 每个查询都带上租户隔离条件。
- **数据权限变更属于 DB2 高风险。** 改权限 = 改谁能看什么，必须确认。

## 21. 数据库与 Git 的关系

### 应进入 Git

- ✅ `prisma/schema.prisma`（数据库结构定义）
- ✅ `prisma/migrations/`（migration 文件）
- ✅ Seed 脚本
- ✅ 脱敏样例数据（明确声明不含真实数据）
- ✅ `.env.example`（含占位 `DATABASE_URL`）
- ✅ 数据库说明文档

### 不得进入 Git

- ❌ 真实 `.env`（含真实 `DATABASE_URL`）
- ❌ 真实数据库文件（`.db`、`.sqlite`、`dump.sql`）
- ❌ 生产备份文件
- ❌ 客户导入文件
- ❌ 客户导出文件
- ❌ 任何包含未脱敏客户数据的文件
- ❌ 数据库密码和真实连接串

### 规则

1. **Git 管代码和结构，不管真实数据。** Schema 在 Git 里，数据在数据库里。
2. **备份文件不是 Git 文件。** 备份有自己的存储和管理方式。
3. **SQLite 真实 `.db` 文件默认不进入 Git。** 已在 `.gitignore` 中。
4. **Migration 文件应进入 Git。** 这是数据库变更历史的唯一记录。
5. **数据库变更必须能从 Git 历史中追踪。** 谁在什么时候加了什么 migration。

## 25. 常见错误与处理

### 25.1 为了解决报错删除数据库

**处理步骤：**
1. 立即停止。不要再做任何数据库操作。
2. 确认这个数据库是否包含真实数据。
3. 检查是否有可用备份。
4. 分析真正导致报错的原因（不是"数据库坏了"，是"哪个操作导致了什么错误"）。
5. 不得继续扩大损失（不要继续删其他表）。
6. 记录到安全事件或交付风险中。

### 25.2 Migration 失败

**处理步骤：**
1. 不直接删除 `prisma/migrations/` 中的文件。
2. 仔细阅读 Prisma 的错误信息。
3. 判断当前环境——是开发环境还是生产环境。
4. 判断是否有真实数据受影响。
5. 给出针对性的修复方案（修改 migration SQL、调整 schema、处理数据冲突）。
6. 必要时重新生成正确的 migration。
7. **失败 3 次后停止并询问用户。** 不无限重试。

### 25.3 Seed 失败

**处理步骤：**
1. 不清空真实数据库来"让 seed 能跑"。
2. 检查 seed 数据是否符合当前 schema 约束。
3. 检查是否有唯一键冲突。
4. 检查环境变量是否正确（是不是连到了生产库）。
5. 只在开发或测试环境修复 seed 问题。
6. 记录失败原因到交付报告。

### 25.4 导入数据混乱

**处理步骤：**
1. 停止继续导入。
2. 查看导入日志（成功多少行、失败多少行）。
3. 判断是否可以回滚（有备份就能回滚）。
4. 使用备份恢复或写修复脚本。
5. **不直接批量 DELETE 来"清理"。** 可能删错数据。
6. 复盘问题原因：字段映射错了？校验不够？编码问题？

### 25.5 SQLite 文件丢失或误删

**处理步骤：**
1. 停止运行该程序。
2. 检查是否有备份（`.db.backup` 或手动备份）。
3. 检查 Git 历史中是否存在该文件（不该存在的话检查 `.gitignore`）。
4. 检查最近的删除操作记录。
5. 如果无法恢复，记录数据损失范围。
6. 补充备份机制——问题不在于 SQLite 不好，在于没有备份策略。

## 28. 当前阶段默认结论

1. **长期 AI 产品优先 PostgreSQL。** 扩展性、AI 兼容性、长期演进能力最强。
2. **国内普通商用项目优先 MySQL。** 客户熟悉、运维方便、中国市场普及率最高。
3. **本地工具和快速 MVP 可以用 SQLite。** 零部署成本，开发速度快。
4. **SQLite 真实数据库文件默认不进入 Git。** `.gitignore` 已配置。
5. **Prisma 是当前 TypeScript 项目的默认 ORM。** schema、migration、seed——一体化管理。
6. **数据库 schema 变更属于 DB2 高风险。** 必须分析、确认、备份、可回滚。
7. **Migration 必须先分析影响范围，再确认执行环境，再执行。** 三步缺一不可。
8. **涉及真实数据的操作必须先确认备份存在且可用。**
9. **Claude Code 不得自动删除数据库、清空表、或连接生产数据库。** 这些是 DB3 硬规则。
10. **数据库标准必须先于正式产品开发完成。** 没有数据库管理规范的项目不开工。
