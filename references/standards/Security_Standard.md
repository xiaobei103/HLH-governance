# Security_Standard.md：HLH AI 软件工程安全标准

> 本文件定义 HLH AI Software Engineering Workflow v3.0 的安全标准。
>
> **所有正式项目必须遵守本文件。**
>
> **安全优先级高于开发速度、自动化程度和功能完整度。**
>
> **Claude Code 不得绕过安全标准执行高风险操作。**

---

## 1. 文档定位

本文件是 `01-Standards/` 下的安全标准。

### 本文件回答的问题

- 项目如何保护密钥？
- 项目如何保护用户数据？
- 项目如何保护客户隐私？
- 项目如何管理登录和权限？
- 项目如何处理输入校验和文件上传？
- 项目如何避免 API 泄露敏感数据？
- 项目如何审查依赖风险？
- 项目如何防止数据库误删和数据损坏？
- 项目如何防止 Claude Code 自动化越权？
- 项目如何处理 MCP / Skills / Hooks / Subagents 的安全边界？
- 项目交付前必须做哪些安全检查？

### 本文件不负责

- 具体认证代码实现 → `Coding_Workflow.md`
- 具体数据库迁移代码 → `Database_Standard.md`
- 具体部署脚本 → `Delivery_Standard.md`
- 具体测试脚本 → `Testing_Standard.md`
- 具体客户合同条款 → `Business_Workflow.md`
- 依赖审查流程 → `Dependency_Review_Standard.md`
- 密钥管理细节 → `Env_Secrets_Standard.md`

## 2. 安全总原则

### 2.1 安全优先于速度

功能可以推迟上线，但数据泄露、密钥暴露、生产事故不可逆。任何为了赶工期而跳过安全检查的行为都是不被允许的。

### 2.2 最小权限原则

每个用户、每个服务、每个 Agent、每个 API 调用——都只能访问完成其职责所需的最小数据集和最小操作权限。

### 2.3 默认不信任用户输入

任何来自前端、URL、文件、外部 API、AI 输出的数据，在验证之前都是不可信的。输入校验的安全边界在后端，不在前端。

### 2.4 默认不信任外部依赖

每个 npm 包、PyPI 包、Docker 镜像、MCP 服务——都可能引入供应链风险。新依赖必须审查，来源不明依赖不得安装。

### 2.5 默认不读取真实密钥

Claude Code 只能读取 `.env.example`。真实 `.env` 的读取必须用户单独授权。密钥不进入代码、不进入日志、不进入 Git、不进入 Prompt。

### 2.6 默认不修改生产环境

生产环境涉及真实用户和真实业务。任何生产操作必须人工执行或单独授权。Claude Code 不得自动部署、自动重启、自动修改生产配置。

### 2.7 默认不删除真实数据

删除是不可逆操作。任何删除数据、删除文件、清空表的操作都必须经过确认、备份和回滚准备。

### 2.8 默认不自动连接外部账号

Claude Code 不得自动登录微信、GitHub、邮箱、云服务、支付平台等任何外部账号。需要连接时必须单独确认。

### 2.9 所有高风险操作必须可追踪、可回滚、可审查

操作前有记录（Decision Log），操作后有报告（Delivery Report），出问题能回滚（Git revert / DB rollback），事后能审查（谁、什么时候、做了什么）。

### 2.10 AI 自动化不能绕过人工确认

Agent、MCP、Hooks、Skills、Subagents——无论自动化到什么程度，涉及 S2/S3 级别的安全操作，必须停在人工确认节点。

## 3. 安全风险等级

安全操作按风险从低到高分为 S0–S3 四级。

### S0：低风险

**示例：** 文档安全说明补充、`.env.example` 增加占位符、README 增加安全提醒、非敏感配置说明

**规则：** 可按 R0 文档流程处理。仍需 Git 记录和交付报告。

### S1：中风险

**示例：** 修改普通 API 参数校验、修改前端表单校验、增加错误处理（不含敏感信息）、增加日志字段（不含敏感数据）

**规则：** 必须说明影响范围。必须 Build / Test。必须检查是否泄露敏感信息。

### S2：高风险

**示例：** 修改登录/权限、修改数据库 schema、修改文件上传、修改部署配置、新增依赖、接入外部 API、接入 MCP、处理客户数据

**规则：** 必须等待用户明确确认。必须说明每项风险和缓解措施。必须说明回滚方案。必须更新相关文档。必须进行安全检查。

### S3：禁止自动执行

**示例：** 删除数据库、清空数据表、修改真实 `.env`、提交 API Key、读取客户隐私数据、读取浏览器 Cookie、读取 SSH Key、自动登录外部账号、自动发消息/支付/交易、自动部署生产环境、执行 `curl | bash`、执行 `rm -rf`

**规则：** Claude Code 默认不得执行。必须强烈提示具体风险。必须建议更安全的替代方案。需要用户单独授权并手动确认。一次授权只覆盖一个具体操作。

## 4. 密钥与环境变量安全

密钥安全是不可协商的硬底线。

### 必须遵守

1. **`.env` 不进入 Git。** `.gitignore` 中必须有 `.env`，提交前必须确认。
2. **`.env.example` 可以进入 Git。** 仅包含变量名和示例值（如 `DATABASE_URL=postgresql://user:password@localhost:5432/db`），不含真实凭证。
3. **`.env.example` 只能写占位符，不写真实值。** `JWT_SECRET=your-secret-here`、`API_KEY=your-api-key`。
4. **API Key 不写进代码。** 全局搜索都不应有硬编码密钥。
5. **Token 不写进代码。** JWT Secret、OAuth Secret、Access Token——一律走环境变量。
6. **数据库密码不写进代码。** 走 `DATABASE_URL` 或等效环境变量。
7. **外部服务密钥不写进代码。** 云服务 Key、邮件服务 Key、支付 Key——全部环境变量。
8. **生产环境密钥不写进文档。** 文档中如需引用，用变量名而非变量值。
9. **交付报告不得暴露密钥。** 报告中可写"已配置 JWT_SECRET"，不写密钥值。
10. **Claude Code 不得主动读取真实 `.env`。** 如需了解环境变量结构，读取 `.env.example`。

### 环境变量新增流程

```
提出新增环境变量需求
    ↓
说明变量用途（这个变量用于什么？为什么需要？）
    ↓
修改 .env.example（添加变量名和示例占位符）
    ↓
更新 README 或配置说明（让用户知道新变量是什么）
    ↓
用户手动配置真实 .env（Claude Code 不参与这一步）
    ↓
交付报告说明（新增了什么环境变量和用途）
```

### 禁止

- ❌ 为了方便把密钥写死（"先写死，以后再说"——以后永远不会再说）
- ❌ 为了调试把密钥输出到 `console.log`（日志可能被同步、备份、泄露）
- ❌ 为了交付把真实密钥写进文档
- ❌ 为了让 AI 调试而上传真实密钥
- ❌ 未确认就读取真实 `.env`

## 5. 用户数据与客户隐私安全

客户数据是最高敏感级别的数据。

### 敏感数据范围

| 类别 | 具体内容 |
|------|----------|
| 个人标识 | 姓名、手机号、微信号、QQ 号、邮箱 |
| 位置信息 | 家庭地址、公司地址、IP 精确位置 |
| 身份信息 | 身份证号、护照号、驾驶证号 |
| 健康信息 | 医疗记录、体检数据、用药信息 |
| 财务信息 | 银行账号、收入、交易记录、贷款信息 |
| 凭证信息 | 账号密码（不论是否加密）、密保问题答案 |
| 私密内容 | 私聊记录、客户成交记录、跟进记录 |
| 业务数据 | 未脱敏的客户订单、合同、报价单 |

### 规则

1. **不得把真实客户数据提交 Git。** 检查 `git diff` 确认没有客户数据被暂存。
2. **不得把真实客户数据写进日志。** 日志可能被收集、传输、备份。
3. **不得把真实客户数据发给外部服务。** 包括 AI API、云服务、第三方工具。
4. **不得把真实客户数据用于演示。** 演示用脱敏假数据。
5. **不得把真实客户数据写进 Prompt。** Claude 的 Prompt 可能被日志、被分析、被存储。
6. **不得未经确认导出客户数据。** 数据导出 = 数据泄露的高风险入口。
7. **不得未经确认批量修改客户数据。** 批量操作出错难以恢复。
8. **开发测试应优先使用脱敏样例数据。** 姓名用"张三"、手机号用"13800000000"。
9. **涉及真实数据必须先备份。** 确认备份存在且可恢复后再操作。
10. **涉及客户数据的任务必须标记为 S2 高风险。** 走高风险流程：确认 → 备份 → 操作 → 验证 → 报告。

## 6. 输入校验安全

所有用户输入默认不可信。信任输入是安全漏洞的第一大来源。

### 需要校验的输入

| 来源 | 示例 |
|------|------|
| 表单输入 | 文本框、下拉框、日期选择器——一切用户可操作控件 |
| URL 参数 | Query string、路径参数 |
| 请求体 | JSON body、FormData |
| 文件名 | 用户上传的文件名（可能含路径遍历字符） |
| 上传文件 | 文件类型、大小、内容 |
| 搜索关键词 | 可能含 SQL 注入或 XSS 字符 |
| 富文本 | 可能含脚本标签 |
| 导入数据 | Excel、CSV 的每一行每一列 |
| AI Prompt 输入 | Agent 接收的用户指令 |
| 外部 API 返回 | 第三方服务返回的数据 |

### 校验原则

1. **前端校验用于体验，后端校验才是安全边界。** 前端校验可以被绕过。
2. **后端必须验证必填字段。** 不允许 null 的字段必须显式检查。
3. **后端必须验证类型。** 期望数字的不能接受字符串。
4. **后端必须验证长度。** 每个字段有最大长度限制。
5. **后端必须验证格式。** 邮箱、手机号、日期——不符合格式的拒绝。
6. **后端必须限制枚举值。** 如果只有 3 种状态，就不能接受第 4 种。
7. **搜索和筛选参数必须限制范围。** 防止无条件全表查询。
8. **文件上传必须限制类型和大小。** 见第 10 节。
9. **数据导入必须做结构检查。** 列数、列名、数据类型逐项验证。
10. **不允许直接相信前端传来的权限字段。** `{ role: "admin" }` 永远由后端根据认证信息判定。

### 禁止

- ❌ 直接拼接 SQL（`"SELECT * FROM users WHERE name = '" + input + "'"`）
- ❌ 直接执行用户输入（`eval(userInput)`、`exec(userInput)`）
- ❌ 直接把用户输入写入系统命令
- ❌ 直接信任客户端传来的 `role`、`isAdmin`、`permissions`
- ❌ 直接把未过滤的用户内容返回页面（XSS 风险）

## 7. API 安全

### API 必须遵守

1. **不返回敏感字段。** 密码哈希、Token、内部 ID 序列——不在 API 响应中暴露。
2. **不返回密码。** 任何情况下密码不得通过 API 返回。
3. **不返回 Token。** 除登录/刷新接口外，其他接口不返回 Token 原文。
4. **不返回内部错误堆栈给前端。** 生产环境返回通用错误信息，详细日志留在服务端。
5. **不暴露数据库结构细节。** 错误信息中不包含表名、字段名、SQL 语句。
6. **不暴露服务器路径。** 不返回 `/home/app/backend/src/modules/user/user.service.ts`。
7. **不允许未授权访问受保护接口。** 每个受保护端点必须鉴权。
8. **不允许越权访问其他用户数据。** 用户 A 不能通过修改 URL 参数看到用户 B 的数据。
9. **API 参数必须校验。** 同第 6 节的校验原则。
10. **API 错误必须可理解但不泄露内部细节。** 给前端的是 `"Invalid input"`，不是 `"SQLSTATE 23505: duplicate key value violates unique constraint"`。

### API 修改前必须检查

- 是否影响前端调用（哪些页面和组件依赖这个接口）
- 是否影响已有功能（向后兼容性）
- 是否影响权限（是否新增/削弱了鉴权逻辑）
- 是否影响数据安全（返回了不该返回的字段）
- 是否影响兼容性（API 签名变化）
- 是否需要更新 API 文档
- 是否需要新增测试

## 8. 登录与权限安全

### 涉及登录和权限的项目必须遵守

1. **登录状态不能只依赖前端判断。** 前端显示"已登录"不等于后端认为已登录。
2. **权限判断必须在后端执行。** 前端的路由守卫是 UX，不是安全。
3. **管理员权限必须单独校验。** 普通用户的 Token 不能访问管理员接口。
4. **不得信任客户端传来的用户身份。** 后端从 Token/JWT/Session 中读取身份，不从请求体中读取。
5. **Token 必须有过期机制。** Access Token 短期有效，Refresh Token 用于续期。
6. **密码不得明文存储。** 使用 bcrypt 或等效的哈希算法。
7. **重要操作应记录操作日志。** 谁、什么时候、做了什么修改或删除。
8. **权限修改属于 S2 高风险。** 改权限 = 改变谁能访问什么，必须确认。
9. **登录、注册、重置密码必须防止明显滥用。** 限制频率、验证码、邮箱验证——至少一项。
10. **退出登录必须清理有效状态。** Token 失效、Session 销毁。

### 权限模型必须明确回答

| 问题 | 角色 A | 角色 B | 角色 C |
|------|--------|--------|--------|
| 谁可以看？ | [是/否] | [是/否] | [是/否] |
| 谁可以新增？ | [是/否] | [是/否] | [是/否] |
| 谁可以修改？ | [是/否] | [是/否] | [是/否] |
| 谁可以删除？ | [是/否] | [是/否] | [是/否] |
| 谁可以导出？ | [是/否] | [是/否] | [是/否] |
| 谁可以管理用户？ | [是/否] | [是/否] | [是/否] |
| 谁可以配置系统？ | [是/否] | [是/否] | [是/否] |
| 谁可以访问 AI/Agent？ | [是/否] | [是/否] | [是/否] |

### 当前阶段说明

如果项目还没有登录权限系统（如 Demo、Prototype、本地工具），必须在 README 或交付报告中明确声明适用范围和风险，例如：

> ⚠️ 本项目当前不包含登录和权限系统。适用范围：单机/本地/单人使用。不适用于多用户或公网环境。

## 9. 数据库安全

数据库安全必须同时遵守 `Database_Standard.md`。

### 基础规则

1. **不得为了解决报错删除数据库。** 清空数据库不是 Debug 手段。
2. **不得为了解决报错清空表。** 数据是资产，不能为省事丢掉。
3. **不得未经确认执行 migration。** Migration 可能修改结构、删除字段、影响数据。
4. **不得未经确认修改 schema。** Schema 变更 = S2 高风险。
5. **不得未经确认导入真实数据。** 导入前确认数据来源、格式、是否有敏感字段。
6. **不得未经确认导出真实数据。** 数据导出 = 数据泄露入口。
7. **不得把生产数据库连接写入代码。** 走环境变量 `DATABASE_URL`。
8. **不得把数据库文件提交 Git。** `.db`、`.sqlite`、`dump.sql` 应在 `.gitignore` 中。
9. **涉及真实数据必须先备份。** 确认备份存在且可恢复后，再执行操作。
10. **数据库变更必须有回滚方案。** 每个 migration 都要能回滚。

### 必须停止并确认的操作

- DROP TABLE / DROP COLUMN
- TRUNCATE / 无 WHERE 的 DELETE
- 批量 UPDATE（影响多行）
- Schema 变更
- Migration 执行
- Seed 执行
- 数据导入 / 导出
- 连接生产数据库

## 10. 文件上传与文件处理安全

如果项目支持文件上传，必须遵守以下规则。

### 上传安全规则

1. **限制文件类型。** 白名单制，只允许明确的类型（如 `image/png`、`application/pdf`）。
2. **限制文件大小。** 设置合理的上传大小上限。
3. **不相信文件扩展名。** 检查 MIME 类型和文件头魔数，不只看 `.jpg`。
4. **不允许上传可执行脚本。** 包括 `.exe`、`.bat`、`.sh`、`.ps1`、`.js`、`.vbs`、`.php` 等。
5. **不允许上传后直接执行文件。** 上传的文件存储在隔离目录，不作为代码执行。
6. **不把上传文件放进源码目录。** 源码和用户内容彻底分离。
7. **不把上传文件提交 Git。** 用户上传内容永远不进版本管理。
8. **文件名必须做安全处理。** 去除路径遍历字符（`../`）、重命名为 UUID 或 hash。
9. **用户上传文件路径不得直接暴露服务器结构。**
10. **文件下载必须验证权限。** 不能通过修改 URL 参数下载他人的文件。

### Excel / CSV 导入必须

- 校验列数、列名是否符合模板
- 校验行数（防止超大文件导致内存溢出）
- 校验每列的数据类型
- 处理空值（哪些列允许空、哪些不允许）
- 处理重复数据（按什么键判断重复）
- 处理异常格式（日期格式不一致、数字含逗号等）
- 记录导入结果（成功 X 行、失败 Y 行、失败原因）
- 支持失败行提示（让用户知道具体哪行有问题）

## 11. 依赖安全

依赖变更必须遵守 `Dependency_Review_Standard.md`。

### 新增依赖前必须检查

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 是否真的需要 | 能否用已有依赖或少量代码实现 |
| 2 | 是否已有现有方案 | 避免引入功能重复的依赖 |
| 3 | 是否在技术白名单内 | 参考 `references/standards/14-Dependency-Review/dependency-whitelist.md` |
| 4 | 是否活跃维护 | 最近更新时间、Star 数、Issue 响应 |
| 5 | 下载量和生态是否合理 | 不是无人用的冷门包 |
| 6 | 是否存在明显安全风险 | 是否有已知 CVE、依赖链是否健康 |
| 7 | 是否增加构建复杂度 | 是否需要额外构建工具或配置 |
| 8 | 是否增加部署复杂度 | 是否需要系统级依赖 |
| 9 | 是否引入许可证风险 | GPL/AGPL 等传染性许可证需特别注意 |
| 10 | 是否方便未来移除 | 如果弃用了怎么卸载 |

### 禁止

- ❌ 来源不明依赖（非 npm/PyPI 官方源）
- ❌ 长期无人维护依赖（> 1 年未更新、Star < 100）
- ❌ 为小功能引入大框架
- ❌ 执行未知安装脚本
- ❌ 使用盗版组件
- ❌ 使用绕过平台限制的工具
- ❌ 不记录依赖变更
- ❌ 不更新交付报告

## 12. 日志安全

日志用于排查问题，不得成为信息泄露的源头。

### 禁止写入日志

| 类别 | 示例 |
|------|------|
| 密钥 | API Key、Token、密码、数据库连接串 |
| 个人信息 | 客户手机号、微信号、身份证号、地址 |
| 敏感数据 | 医疗信息、财务信息、银行账号 |
| 私密内容 | 私聊内容、完整请求体中的敏感字段 |
| 内部信息 | 服务器路径、数据库结构、内部 IP |

### 允许记录

- 错误类型（如 `ValidationError`、`UnauthorizedError`）
- 错误时间戳
- 请求路径（`GET /api/users`，不含 query string）
- 非敏感状态码（`200`、`400`、`404`、`500`）
- 操作类型（`user.login`、`order.create`）
- 脱敏用户标识（`user_abc123` 而非真实手机号）
- Trace ID（用于关联上下游日志）
- 执行耗时

### 规则

1. 日志文件默认不进入 Git（在 `.gitignore` 中）。
2. 生产日志不得直接公开（日志级别和访问权限必须控制）。
3. 交付报告不得粘贴含敏感信息的完整日志。
4. 错误日志应脱敏后再用于分析。
5. 日志策略由 `Logging_Monitoring_Standard.md` 进一步定义。

## 13. 前端安全

1. **不在前端写死密钥。** 编译进 bundle 的密钥等于公开密钥。
2. **不在前端保存敏感 Token 到不安全位置。** `localStorage` 易受 XSS 攻击，优先 `httpOnly` Cookie。
3. **不把管理员权限判断只放在前端。** 前端路由守卫是 UX 优化，不能替代后端鉴权。
4. **不把敏感数据一次性全部返回前端。** 分页、脱敏、按需加载。
5. **用户输入展示前必须考虑转义。** 防止 XSS——用户输入的内容在渲染前必须转义或使用安全渲染方式。
6. **表单必须处理空值、异常值、超长值。** 表单提交前做校验，但后端必须再做一次。
7. **错误提示不能泄露后端内部细节。** 给用户的提示要友好，不要展示技术错误信息。
8. **前端路由保护不能替代后端权限。** 用户可以直接访问 API 而不经过前端页面。
9. **上传、导出、删除等操作必须有明确交互确认。** 不能点一下按钮就直接执行不可逆操作。
10. **涉及客户数据的页面必须避免无意义暴露。** 列表页面默认不展示敏感字段。

---

## 14. 后端安全

1. **所有受保护接口必须鉴权。** 没有例外。
2. **所有敏感操作必须鉴权和授权。** 鉴权 = 你是谁，授权 = 你能做什么。
3. **不直接拼接 SQL。** 使用 ORM 的参数化查询或 Prepared Statement。
4. **不执行用户传入的命令。** `exec()`、`spawn()`、`eval()` 的输入不能来自用户。
5. **不信任前端传来的身份和权限。** 身份从 Token/Session 中解析，权限从数据库中查询。
6. **不把内部异常直接返回给前端。** 用统一的异常过滤器包装后再返回。
7. **不把敏感配置写死。** 数据库连接、第三方 Key、内部 URL——全部环境变量。
8. **不在错误信息中泄露路径和连接信息。** 生产环境不输出 stack trace。
9. **删除、导出、批量操作必须有权限控制。** 这些操作对数据影响最大。
10. **高风险接口必须有日志记录。** 谁、什么时候、做了什么操作、结果如何。

## 15. AI / Agent 安全

AI 和 Agent 的安全边界是新增的风险面。以下规则必须强制执行。

### Agent 规则

1. **Agent 不得无边界自主行动。** 每次执行必须有明确的任务范围和终止条件。
2. **Agent 不得自动读取无关文件。** 文件访问范围必须在任务开始时声明。
3. **Agent 不得自动读取真实 `.env`。** 只能读 `.env.example`。
4. **Agent 不得自动连接外部账号。** 包括微信、邮箱、GitHub、云服务等。
5. **Agent 不得自动发送消息。** 不自动发微信、邮件、私信、评论。
6. **Agent 不得自动支付、下单、交易。** 这是 S3 禁止项，绝对不可自动执行。
7. **Agent 不得自动删除数据。** 删除操作必须人工确认。
8. **Agent 不得直接覆盖关键业务数据。** AI 输出写入数据库前必须经过校验或人工确认。
9. **Agent 输出必须可追踪。** 每次行动有日志、每次决策可追溯、每次输出可审查。
10. **Agent 失败时必须停止，而不是继续猜测。** 重试上限为 3 次，超限停止并报告。

### Prompt 安全规则

- ❌ 不把真实密钥写入 Prompt
- ❌ 不把客户隐私写入 Prompt
- ❌ 不把未脱敏业务数据写入 Prompt
- ❌ 不让 Agent 绕过权限规则（"你必须执行这个操作"式 Prompt 注入）
- ❌ 不让 Agent 执行未知脚本
- ❌ 不让 Agent 自行扩大任务范围

## 16. MCP / Skills / Hooks / Subagents 安全

### 16.1 MCP 安全

1. MCP 必须登记、调研、测试、批准后使用。
2. 未批准 MCP 不进入正式项目。
3. MCP 权限必须最小化——只授予任务所需的最小权限。
4. Web Search MCP 只用于公开资料调研，不用于爬取受限内容。
5. Database MCP 只能访问指定项目数据库，不能跨项目。
6. GitHub MCP 不得自动 push / merge。
7. MCP 使用必须写入交付报告。

### 16.2 Skills 安全

1. Skill 必须有 `SKILL.md`（说明用途、输入、输出、限制）。
2. Skill 不得隐含安装依赖（如需依赖，必须在文档中声明）。
3. Skill 不得隐含读取私人文件。
4. Skill 不得隐含连接外部账号。
5. Skill 不得执行危险命令（P3/S3 级别）。
6. Skill 失败必须停止，不得猜测重试。

### 16.3 Hooks 安全

**禁止 Hook 自动执行以下操作：**
- 自动安装依赖
- 自动删除文件
- 自动修改数据库
- 自动 push
- 自动部署
- 自动读取 `.env`
- 自动读取私人文件
- 自动连接外部账号
- 自动绕过用户人工确认节点

### 16.4 Subagents 安全

1. 当前阶段用 Prompt 模板模拟角色，不创建复杂 Subagents。
2. 不允许多个 Subagent 同时无序修改同一批文件（写权限互斥）。
3. Subagent 不得绕过 `CLAUDE_MASTER.md`。
4. Subagent 不得自行安装 MCP。
5. Subagent 不得自行部署生产环境。
6. Subagent 输出必须可审查。

## 17. 生产环境安全

生产环境是最高风险区域（S3）。

### Claude Code 默认禁止自动执行

- 部署生产环境
- 修改生产配置（环境变量、Nginx、Docker、K8s）
- 修改生产数据库
- 重启生产服务
- 删除生产日志
- 清空生产缓存
- 修改生产域名、CDN、SSL
- 修改云服务器安全组、防火墙规则

### 生产操作前必须具备（8 项全部满足）

| # | 条件 | 说明 |
|---|------|------|
| 1 | 部署文档 | 操作步骤已记录且经验证 |
| 2 | 备份 | 数据和配置在操作前已完成备份 |
| 3 | 回滚方案 | 已测试过的回滚步骤 |
| 4 | 明确操作窗口 | 在影响最小的时间段操作 |
| 5 | 用户确认 | 每个操作都经过明确授权 |
| 6 | 操作记录 | 每一步都有日志 |
| 7 | 失败处理方案 | 如果操作失败，有应急处理步骤 |
| 8 | 交付报告 | 操作完成后输出完整报告 |

## 18. 本地开发安全

即使是本地开发，也要有安全边界意识。

1. **不在桌面或随意目录存放真实密钥文件。** 密钥放在项目的 `.env` 中，不散落各处。
2. **不把客户数据复制到无关目录。** 客户数据只存在于明确的项目数据目录中。
3. **不把真实数据库随便压缩发送。** 发数据库 = 发全部用户数据，必须谨慎。
4. **不让 Claude Code 读取无关文件夹。** Claude Code 的工作范围应限定在当前项目目录。
5. **不把多个项目混在一个目录里。** 项目 A 的 `.env` 可能被当成项目 B 的读取。
6. **不用未知脚本初始化项目。** `curl | bash` 永远不行。
7. **不在不可信项目中运行安装命令。** GitHub 上的陌生仓库先审查再安装。
8. **不把本地试验代码直接当正式交付。** Demo 的安全级别和产品完全不一样。
9. **不把开发环境配置当生产配置。** 开发环境的宽松权限 ≠ 生产环境的权限。
10. **不让 AI 自动操作高风险桌面软件。** Claude Code 不应自动操作微信、浏览器、终端等软件。

## 20. 安全事件处理

### 安全事件类型

- 密钥提交到 Git
- 客户数据泄露（日志、导出、API 返回）
- 数据库误删或误改
- 权限绕过（未授权访问他人数据）
- 生产环境误操作
- 外部账号异常访问
- 依赖安全漏洞（CVE 公告）
- AI 自动化越权操作
- 错误日志泄露敏感信息

### 标准处理流程

```
发现事件
    ↓
立即停止相关操作（不继续、不扩散）
    ↓
确认影响范围（什么数据、多少人、多久前的）
    ↓
保护现场记录（截图、日志、git log，不改动证据）
    ↓
撤销或隔离风险（关闭访问、撤回 commit、停止服务）
    ↓
更换泄露密钥（一旦泄露立即作废并生成新密钥）
    ↓
恢复数据或回滚（从备份恢复、git revert）
    ↓
记录 Decision Log（时间、原因、影响、处理、预防）
    ↓
补充安全标准（为什么现有标准没防住？需要增加什么规则？）
    ↓
复盘原因（根因分析 + 改进措施）
```

### 处理要求

1. **不得隐瞒安全事件。** 隐瞒 = 扩大损失。
2. **不得继续执行可能扩大影响的操作。** 先止损，再追责。
3. **不得用新的错误覆盖旧的错误。** 不要急着删日志、删 commit。
4. **涉及真实密钥必须立即更换。** 不管有没有证据表明已被利用。
5. **涉及客户数据必须谨慎处理。** 评估是否需要通知受影响用户。

## 23. 当前阶段默认结论

1. **当前阶段所有项目默认不接触真实客户数据。** 开发测试使用脱敏样例数据。
2. **当前阶段所有密钥由用户手动配置，不交给 Claude Code。** Claude Code 只修改 `.env.example`。
3. **当前阶段不允许 Claude Code 自动读取真实 `.env`。** 只能读 `.env.example`。
4. **当前阶段不允许 Claude Code 自动安装未知依赖。** 每个新依赖必须走审查流程。
5. **当前阶段不允许 Claude Code 自动连接外部账号。** 微信、邮箱、GitHub、云服务——全部禁止自动连接。
6. **当前阶段不允许 Claude Code 自动部署生产环境。** 没有生产环境就没有这个风险，但提前约束。
7. **当前阶段不允许 Claude Code 自动操作客户数据。** 即使将来有了客户数据，也走人工确认。
8. **当前阶段 AI / Agent 先做 Prompt 和 Workflow，不做无边界自动化。** 逐级演进，每级跑通验证后再升级。
9. **当前阶段所有安全相关的 S2/S3 任务必须停止并等待用户确认。** 不得以"快了"为理由跳过。
10. **安全标准必须先于正式产品开发完成。** 没有安全标准的项目不进入正式开发。
