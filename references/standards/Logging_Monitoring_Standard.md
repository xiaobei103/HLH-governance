# Logging_Monitoring_Standard.md：HLH AI 软件工程日志与监控标准

> 本文件定义 HLH AI Software Engineering Workflow v3.0 的日志与监控标准。
>
> **所有正式项目必须具备可排查、可追踪、可审查的日志策略。**
>
> **日志不得泄露密钥、客户隐私、真实数据库连接、Token 或外部账号凭证。**
>
> **当前阶段优先建立轻量日志规范，不急于引入复杂监控平台。**

---

## 2. 日志与监控总原则

### 2.1 日志用于定位问题，不用于堆垃圾

每一条日志都应该有排查价值。`console.log('here')`、`console.log('test')` 这种无信息量的日志就是垃圾。要么写有意义的信息，要么不写。

### 2.2 错误必须可追踪

任何错误发生，日志必须能回答：什么时间、哪个模块、什么错误类型、影响什么、是否和本次修改有关。

### 2.3 敏感信息不得进入日志

API Key、Token、密码、数据库连接串、客户隐私——这些信息一旦进入日志文件，就可能被备份、被同步、被泄露。日志只记录必要摘要。

### 2.4 客户隐私不得进入日志

手机号、微信号、身份证、地址、医疗信息、财务信息——一律不得以明文形式出现在日志中。

### 2.5 生产日志不得随意公开

生产日志可能包含业务数据、用户行为、系统架构等敏感信息。默认不公开，访问需要权限控制。

### 2.6 日志默认不进入 Git

日志文件是运行时产物，不是源码。`.gitignore` 中排除 `*.log` 和 `logs/*.log`。日志配置和规范文档可以进入 Git。

### 2.7 关键操作必须有审计记录

谁在什么时候做了什么操作（删除、导出、修改权限、连接生产环境）——这些必须可追溯。

### 2.8 Agent 行为必须可追踪

Agent 的每次任务、每个工具调用、每次失败和重试——都应该有日志记录。Agent 是黑盒运行时，没有日志就无法排查。

### 2.9 监控复杂度必须匹配项目阶段

Prototype 不需要 Grafana + Prometheus + ELK 全家桶。一个 `console.error` 和交付报告中的手动检查就足够了。监控随项目阶段逐步加。

### 2.10 当前阶段优先轻量可用，不追求企业级监控炫技

Phase 1 的任务是写规范，不是搭监控平台。当前阶段：日志规范先行，监控工具后置。

## 3. 日志风险等级

### L0：低风险

**示例：** 修改日志说明文档、增加日志规范、增加 README 中的错误排查说明、增加交付报告中的日志检查项

**规则：** 按 R0 文档任务处理。仍需 Git commit 和交付报告。

### L1：中风险

**示例：** 增加普通错误日志、增加开发环境调试日志、增加非敏感操作记录、增加 API 错误摘要

**规则：** 必须检查是否包含敏感信息。必须避免输出完整请求体。必须写入交付报告。

### L2：高风险

**示例：** 增加登录/权限日志、增加客户数据相关日志、增加数据库操作日志、增加 Agent 工具调用日志、增加外部 API 调用日志、增加生产环境日志策略

**规则：** 必须等待确认。必须脱敏。必须说明存储位置和保留策略。必须进行安全检查。

### L3：禁止自动执行

**示例：** 记录 API Key/Token/真实 `.env`/数据库密码/客户手机号/微信号/身份信息/完整私聊内容/浏览器 Cookie、自动上传生产日志到外部服务、自动读取私人日志文件、自动清空生产日志

**规则：** Claude Code 默认不得执行。必须提示风险。必须提供脱敏替代方案。涉及生产日志必须单独确认。

## 4. 日志级别标准

| 级别 | 用途 | 生产环境 | 示例 |
|------|------|----------|------|
| **DEBUG** | 开发阶段排查细节 | 默认关闭 | 变量状态、流程分支、临时调试 |
| **INFO** | 正常业务流程和关键状态 | 开启 | 服务启动、API 请求摘要、任务完成 |
| **WARN** | 异常但系统仍可运行 | 开启 | 参数缺失有默认值、外部服务响应慢、重试 |
| **ERROR** | 明确失败或异常 | 开启 | API 失败、数据库连接失败、Agent 工具调用失败 |
| **FATAL** | 系统无法继续运行 | 开启 | 服务启动失败、数据库不可用、核心配置缺失 |

### 规则

1. **日志级别必须真实。** 不能把 ERROR 标成 INFO 来"减少红色"。
2. **不得用 DEBUG 淹没关键错误。** 生产环境控制 DEBUG 输出。
3. **不得把 ERROR 当 INFO。** ERROR 就是需要关注的问题。
4. **FATAL 必须立即引起注意。** 这不是可以忽略的日志。
5. **生产环境应控制 DEBUG 级别。** 避免日志爆炸和性能影响。

## 5. 禁止写入日志的内容

| 类别 | 具体内容 |
|------|----------|
| 密钥 | API Key、Token、Refresh Token、JWT Secret、Session Secret |
| 数据库凭证 | 数据库密码、`DATABASE_URL` 完整值 |
| 服务凭证 | SMTP_PASSWORD、云服务 Secret、SSH Key |
| 会话 | 浏览器 Cookie、完整 Authorization Header |
| 配置 | 真实 `.env` 文件内容 |
| 客户隐私 | 手机号、微信号、身份证号、家庭/公司地址 |
| 敏感信息 | 医疗信息、财务信息、银行账号 |
| 私密内容 | 私聊完整内容、客户跟进记录原文 |
| 业务数据 | 支付信息、股票交易凭证、真实客户导入文件内容 |
| 外部凭证 | 外部账号登录状态、第三方服务 Token |

### 规则

1. **日志只能记录必要摘要。** 需要详细信息时脱敏后再记录。
2. **不得为了调试打印完整对象。** `console.log(req.body)` 可能在 body 中包含密码或客户数据。
3. **不得打印完整 request headers。** Authorization 和 Cookie 在其中。
4. **不得打印 `.env` 变量值。** 只检查是否存在，不打印值。
5. **不得把敏感日志粘贴进交付报告。** 报告引用日志时再次脱敏确认。
6. **不得把敏感日志提交 Git。** 日志文件应在 `.gitignore` 中。

## 6. 日志脱敏规则

### 常见脱敏方式

| 原始值 | 脱敏后 |
|--------|--------|
| `13812345678` | `138****5678` |
| `zhangsan@example.com` | `z***@example.com` |
| `sk-abc123...xyz789` | `sk-****789` |
| `postgresql://user:pass@host:5432/db` | `postgresql://USER:****@HOST:PORT/DB` |
| `450123199001011234` | `450***********1234` |
| `wx_zhangsan123` | `wx_****123` |

### 规则

1. **只保留排查所需的最小信息。** 脱敏后的数据不再能识别个人身份。
2. **不得保留完整密钥。** 密钥脱敏后只保留最后几位用于识别用的是哪个 Key。
3. **不得保留完整客户身份信息。** 姓名、手机号、身份证——脱敏到不可复原。
4. **不得在日志中保留可直接复原的敏感数据。**
5. **脱敏逻辑本身应测试。** 确认脱敏不会意外漏掉某些字段。
6. **脱敏失败时宁可不记录，也不要泄露。** 安全 > 完整。
7. **交付报告中引用日志时必须再次检查脱敏。** 报告中的日志片段也是日志。

## 7. 前端日志标准

### 适用场景

页面加载错误、API 调用失败、表单提交失败、路由跳转异常、页面白屏、组件渲染异常、关键交互失败

### 规则

1. **不在前端日志中输出密钥。** 前端 bundle 是公开的，前端的日志也是。
2. **不输出完整用户隐私数据。** 用户输入的内容即使在前端 console 也不应包含敏感信息。
3. **不输出完整 Token。** 不 `console.log(token)`。
4. **不输出完整 API 响应中的敏感字段。**
5. **生产环境应减少 `console.log`。** 考虑在构建时移除或使用条件判断。
6. **错误提示应对用户可理解。** "网络错误，请稍后重试" 优于 "TypeError: Cannot read properties of undefined"。
7. **技术细节应进入开发日志，不暴露给普通用户。**
8. **前端日志不得替代后端安全检查。** 前端日志是 UX 辅助，不是安全手段。
9. **表单错误应说明哪个字段有问题，不暴露后端内部结构。**
10. **交付前应检查浏览器控制台是否有明显红色报错。**

## 8. 后端日志标准

### 适用场景

服务启动、环境检查、API 请求摘要、数据库连接状态、任务执行状态、外部服务调用结果、错误处理、权限拒绝、导入导出结果、Agent 任务执行结果

### 推荐日志字段

| 字段 | 说明 | 示例 |
|------|------|------|
| `timestamp` | 日志时间 | `2026-06-30T12:00:00.000Z` |
| `level` | 日志级别 | `INFO` / `ERROR` |
| `requestId` | 请求追踪 ID | `req_abc123` |
| `method` | HTTP 方法 | `GET` / `POST` |
| `path` | 请求路径 | `/api/customers` |
| `statusCode` | 响应状态码 | `200` / `400` / `500` |
| `durationMs` | 请求耗时 | `45` |
| `message` | 日志摘要 | `Customer list queried successfully` |
| `errorCode` | 错误码 | `CUSTOMER_NOT_FOUND` |
| `userIdMasked` | 脱敏用户标识 | `user_****789` |
| `action` | 操作类型 | `customer.create`、`order.export` |

### 规则

1. **启动时可记录环境名称（`NODE_ENV=production`），不打印真实密钥。**
2. **API 日志应记录：路径、方法、状态码、耗时。** 这四项足够排查大部分问题。
3. **不记录完整请求体。** Body 可能包含密码、客户数据、Token。
4. **不记录 Authorization header。**
5. **不记录 Cookie。**
6. **错误日志应记录错误类型和摘要，不记录完整堆栈中的敏感参数。**
7. **不把内部堆栈直接返回前端。** 生产环境用通用错误响应。
8. **生产日志应避免过度详细。** 每条日志都消耗磁盘和 I/O。
9. **高风险操作（删除、导出、权限修改）应有审计日志。**
10. **后端日志文件默认不进入 Git。**

## 9. API 日志标准

### 应记录

- 请求时间
- 请求方法（GET/POST/PUT/DELETE）
- 请求路径（不包含 query string 中的敏感参数）
- 响应状态码
- 响应耗时（ms）
- 错误码（如有）
- 请求 ID（用于关联上下游）
- 脱敏用户标识
- 操作类型

### 禁止记录

- 完整 request body
- 完整 response body
- Authorization header
- Cookie
- API Key（即使在 header 中）
- Token
- 密码（即使在 body 中）
- 客户隐私字段

### API 错误日志必须能回答

| # | 问题 |
|---|------|
| 1 | 哪个接口出错？（路径 + 方法） |
| 2 | 什么时间出错？ |
| 3 | 是客户端错误（4xx）还是服务端错误（5xx）？ |
| 4 | 是否影响核心业务流程？ |
| 5 | 是否可以复现？ |
| 6 | 是否和本次修改有关？ |
| 7 | 是否需要回滚？ |

## 10. 数据库日志标准

### 适用场景

连接成功/失败、查询失败、migration 结果、seed 结果、导入导出结果、数据库连接异常、事务失败、备份结果、回滚结果

### 规则

1. **不记录完整 `DATABASE_URL`。** 记录 `Database connected successfully` 即可。
2. **不记录数据库密码。**
3. **不记录完整 SQL 参数中的敏感数据。** 查询参数可能包含客户手机号等。
4. **不记录客户隐私数据。**
5. **Migration 日志必须说明执行环境。** 开发？测试？生产？
6. **Seed 日志必须说明目标环境。**
7. **导入导出日志必须记录：成功行数、失败行数、失败原因摘要。**
8. **批量操作必须记录操作摘要。** "批量更新 150 条记录的状态" 优于逐条打印。
9. **生产数据库错误必须谨慎处理。** 日志中不暴露表结构和连接信息。
10. **数据库日志必须同时遵守 `Database_Standard.md`。**

## 11. 安全日志与审计日志标准

### 安全日志适用场景

登录成功/失败、权限拒绝、数据导出、数据删除、权限修改、配置修改、环境变量说明修改、高风险接口访问、Agent 高风险工具调用、生产环境操作

### 审计日志应记录

| 字段 | 说明 |
|------|------|
| 谁操作 | 脱敏用户标识 |
| 什么时候操作 | 精确时间戳 |
| 操作类型 | `user.login`、`customer.delete`、`data.export` |
| 操作对象 | 哪个资源被操作（ID 或脱敏标识） |
| 操作结果 | 成功/失败 |
| 失败原因 | 摘要（不包含敏感信息） |
| requestId | 用于关联其他日志 |

### 禁止

- 审计日志记录密码
- 审计日志记录完整 Token
- 审计日志记录完整客户隐私
- 审计日志直接暴露给无权限用户

### 规则

1. **重要业务操作必须可追踪。** 删了什么、谁删的、什么时候删的。
2. **删除、导出、权限修改必须记录审计日志。**
3. **审计日志不得随意删除。** 删除审计日志本身就需要审计。
4. **审计日志的访问也应受权限控制。**
5. **当前 MVP 阶段可先用简化的审计记录。** 不用一开始就建完整的审计系统。

## 12. Agent / AI 日志标准

Agent 和 AI 的行为是不确定的，所以日志尤为重要。

### 建议记录

| 字段 | 说明 |
|------|------|
| Agent 名称 | 哪个 Agent 在执行 |
| 任务 ID | 用于追踪整个任务链 |
| 输入摘要 | 用户问了什么（脱敏后） |
| 输出摘要 | Agent 做了什么（脱敏后） |
| Prompt 版本 | 使用的 Prompt 模板版本 |
| 调用的工具 | 调用了哪些工具、参数摘要 |
| 工具调用结果 | 成功/失败、耗时 |
| 是否触发人工确认 | 是否在某个节点停下来等用户 |
| 是否被权限策略阻止 | P2/P3 权限拦截 |
| 是否失败 | 失败原因摘要 |
| 最终状态 | 完成/部分完成/失败/被用户中断 |

### 禁止记录

- 完整客户隐私输入
- 完整密钥
- 完整 `.env` 内容
- 未脱敏业务数据
- 外部账号 Token
- 用户私人文件内容

### 规则

1. **Agent 行为必须可追踪。** 没有日志的 Agent = 黑盒 = 不可信任。
2. **Agent 工具调用必须可审查。** 每次调用什么工具、什么参数、什么结果。
3. **Agent 不得用日志绕过权限。** 不能因为"要记录日志"就读取敏感文件。
4. **Agent 失败时必须记录失败原因。** "失败了"不够——要写清楚什么步骤失败、错误信息是什么。
5. **Agent 输出不得直接覆盖关键业务数据。** 写入前需校验或人工确认。
6. **Agent 日志必须遵守 `permission-policy.md`。**
7. **AI 输出测试结果应写入交付报告或测试记录。**
8. **当前阶段先记录摘要，不做复杂的 Agent 全链路追踪系统。**

## 13. MCP / Skills / Hooks / Subagents 日志标准

### 13.1 MCP 日志

**必须记录：** MCP 名称、状态、调用目的、权限范围、调用结果、是否访问外部服务、是否失败、是否写入交付报告

**禁止记录：** MCP 读取到的敏感原文、外部账号 Token

### 13.2 Skills 日志

**必须记录：** Skill 名称、版本、输入摘要、输出摘要、是否成功、是否触发限制、是否失败

### 13.3 Hooks 日志

**必须记录：** Hook 名称、触发时机、执行动作、执行结果、是否阻止了危险操作

**禁止 Hooks 自动执行：** 读取 `.env`、删除文件、push、部署、修改数据库

### 13.4 Subagents 日志

**必须记录：** Subagent 名称、职责、输入任务、输出结果、修改建议、是否实际修改了文件、是否需要人工确认

**规则：** Subagent 输出必须可审查。不得无序并发修改同一批文件。

## 14. 错误处理与日志关系

### 错误日志应包含

- 错误时间
- 错误级别（ERROR / FATAL）
- 错误位置（哪个模块、哪个文件）
- 错误类型（`ValidationError`、`DatabaseError`、`NetworkError`）
- 错误摘要（不含敏感信息）
- requestId
- 相关操作（用户在执行什么操作时报错）
- 是否可重试
- 是否影响用户
- 是否需要人工处理

### 错误日志不应包含

- 密钥
- 完整请求体
- 客户隐私
- 数据库密码
- Token
- Cookie

### 规则

1. **错误必须真实记录。** 不能 catch 了然后什么都不做。
2. **不得吞掉错误。** `try { ... } catch (e) {}` 是 Bug 的来源。
3. **不得只写"失败了"这种废话。** 写清楚什么失败了、为什么失败。
4. **不得把错误堆栈完整暴露给前端用户。** 前端显示友好的错误提示，详细堆栈留在服务端日志。
5. **交付报告应引用错误摘要，不粘贴含敏感信息的完整日志。**
6. **Build/Test 失败也应记录在交付报告中。**

## 15. 性能指标标准

正式项目可逐步记录以下性能指标，当前阶段不强制。

### 常见指标

| 指标 | 说明 |
|------|------|
| API 响应时间 | p50、p95、p99 |
| 页面加载时间 | FCP、LCP |
| 数据库查询耗时 | 慢查询 > 阈值 |
| Agent 执行耗时 | 单次任务耗时 |
| 外部 API 响应时间 | 第三方服务耗时 |
| Build 耗时 | CI 构建时间 |
| Test 耗时 | 测试套件运行时间 |
| 错误率 | 5xx / 总请求 |
| 请求量 | QPS / RPM |
| 任务成功率 | Agent 任务成功/总数 |

### 规则

1. **性能指标必须服务真实问题。** 有慢查询才去监控查询耗时。
2. **不为了显得"企业级"而堆监控面板。**
3. **性能日志不得泄露敏感参数。**
4. **性能问题应能定位到接口、页面或任务。**
5. **Agent 性能应记录任务耗时和失败原因。**

## 16. 健康检查标准

长期后端项目应考虑健康检查端点。

### 健康检查内容

| 检查项 | 优先级 | 说明 |
|--------|--------|------|
| 服务是否启动 | 必须 | 最基本 |
| 数据库是否可连接 | 必须 | 连不上数据库 = 服务不可用 |
| Redis 是否可连接 | 按需 | 如果使用 Redis |
| 外部服务是否可用 | 按需 | 关键第三方服务 |
| 必要环境变量是否存在 | 建议 | 缺失时不崩溃但告警 |
| Agent 工具是否可用 | 按需 | Agent 项目的特有检查 |

### 健康检查端点示例

```
GET /health
GET /api/health
```

### 规则

1. **健康检查不得泄露密钥。** 不返回 `DATABASE_URL`。
2. **健康检查不得返回完整配置。** 只返回服务状态。
3. **健康检查不得暴露数据库连接串。**
4. **健康检查只返回必要状态。** `{ status: "ok", db: "connected" }` 足够了。
5. **生产环境健康检查应考虑访问控制或限流。** 防止被滥用。

## 17. 告警策略标准

当前阶段不强制复杂告警。正式产品阶段可逐步考虑。

### 值得告警的事件

- 服务不可用
- 数据库连接失败
- 错误率异常升高
- 登录失败异常增多（可能的暴力破解）
- 导入导出异常
- Agent 任务连续失败（≥ 3 次）
- 外部 API 连续失败
- 生产环境配置缺失
- 安全风险触发（权限拒绝激增、异常导出）

### 规则

1. **告警必须有处理人。** 告警发了没人看 = 噪音。
2. **告警必须可理解。** "CPU 85%" 比 "警报 #38473" 有用。
3. **告警不能过度。** 一天 500 条告警 = 0 条有效告警。
4. **告警不得包含密钥。**
5. **告警不得包含客户隐私。**
6. **当前个人阶段先用手动检查 + 交付报告替代复杂告警系统。**
7. **商业项目上线后再逐步建立告警规则。**

## 18. 日志存储与保留策略

### 日志可以存储在哪里

- 控制台输出（开发环境）
- 本地 `logs/` 目录
- 后端日志文件（按日期滚动）
- 数据库审计表
- 云平台日志服务（生产环境，后期）

### 规则

1. **本地 `logs/` 默认不进入 Git。** `.gitignore` 已覆盖。
2. **生产日志不得公开。** 限制文件权限和访问控制。
3. **敏感日志必须脱敏后再存储。**
4. **日志保留时间应匹配项目阶段。** 开发环境 7 天，生产环境按需求。
5. **不得无限堆积日志导致磁盘爆满。** 设置日志轮转和大小限制。
6. **不得用 Git 保存运行日志。** Git 管代码，不管运行时产物。
7. **商业项目应说明日志存储位置和保留策略。**
8. **客户隐私日志应尽量避免产生。** 不记录就是最安全的。
9. **删除生产日志属于 L3 高风险。** Claude Code 不得自动执行。
10. **交付包不应包含真实运行日志。**

## 19. 日志与 Git 的关系

### 应进入 Git

- ✅ 日志规范文档
- ✅ 日志配置模板（如 `winston.config.ts`、`logger.ts`）
- ✅ 脱敏日志示例（用于说明日志格式）
- ✅ `.gitkeep`（保留空 `logs/` 目录结构）
- ✅ README 中的日志说明

### 不得进入 Git

- ❌ 真实日志文件（`*.log`）
- ❌ 生产日志
- ❌ 包含客户数据的日志
- ❌ 错误堆栈中含密钥的日志
- ❌ 外部账号调用日志
- ❌ Agent 处理真实数据产生的日志

### .gitignore 建议

```gitignore
# Logs
logs/*.log
*.log
error.log
debug.log
production.log

# Test outputs
test-results/
playwright-report/
coverage/
```

### 规则

1. **Git 管理日志规范，不管理真实日志。**
2. **`logs/` 目录可以保留 `.gitkeep`，让目录结构存在。**
3. **真实日志应在交付前清理或确认已排除。**
4. **Claude Code 不得把真实日志提交到 Git。**
5. **交付报告中引用日志片段时必须脱敏。**

## 20. 日志与交付报告

### 交付报告中必须说明

| # | 检查项 |
|---|--------|
| 1 | 是否检查了日志 |
| 2 | 是否存在明显前端错误（控制台红色报错） |
| 3 | 是否存在明显后端错误（500、未捕获异常） |
| 4 | 是否存在数据库错误（连接失败、查询失败） |
| 5 | 是否存在安全风险日志（密钥泄露、越权访问） |
| 6 | 是否存在 Agent 失败日志 |
| 7 | 是否存在 Build/Test 错误 |
| 8 | 错误是否已修复 |
| 9 | 未修复的错误是什么、为什么未修复 |
| 10 | 是否有敏感日志风险 |

### 规则

- **交付报告只写摘要。** "API /api/customers 出现 3 次 500 错误，已修复"。
- **不粘贴敏感日志原文。** 报告中不出现完整的密钥、Token、客户数据。
- **不把"未检查"写成"已检查"。** 没看日志就说没看。
- **不把错误日志隐藏不报。** 发现了错误就要写进报告。

## 24. 常见错误与处理

### 24.1 日志泄露密钥

1. 立即停止传播（删除消息、停止共享）。
2. 删除或隔离泄露的日志文件。
3. 判断是否已进入 Git。
4. 判断是否已发送给外部。
5. **作废并更换密钥。**
6. 记录安全事件。
7. 补充脱敏规则。

### 24.2 日志泄露客户数据

1. 停止继续写入该日志。
2. 确认泄露了哪些字段。
3. 清理或隔离日志文件。
4. 修改日志策略（不再记录这些字段）。
5. 用脱敏或摘要替代。
6. 记录安全事件。

### 24.3 日志太多根本无法排查

1. 降低无意义的 DEBUG 输出。
2. 增加 `requestId` 来串联相关日志。
3. 增加错误分类（按模块、按类型）。
4. 保留关键路径日志，删除无意义重复日志。
5. **不要通过全部关闭日志来"解决"。** 关掉日志 = 放弃排查能力。

### 24.4 没有日志无法定位问题

1. 增加关键失败点的日志。
2. 增加错误摘要（不记录敏感信息）。
3. 增加操作结果记录。
4. 在交付报告中标记"日志不足"风险。
5. 补充日志规范。

### 24.5 Agent 行为不可追踪

1. 增加任务 ID。
2. 记录 Prompt 版本。
3. 记录工具调用摘要。
4. 记录失败原因。
5. 增加人工确认节点日志。
6. **不记录敏感输入原文。**

## 25. 日志与安全事件处理

日志是发现安全事件的重要来源。

### 日志可能暴露的安全事件

多次登录失败、权限拒绝异常增多、数据导出行为异常、数据删除异常、Agent 越权尝试、MCP 调用异常、外部 API 调用异常、数据库错误异常、环境变量缺失、生产服务异常

### 处理流程

```
发现异常日志
    ↓
停止相关高风险操作
    ↓
判断是否为安全事件
    ↓
确认影响范围（什么数据、多少用户、多长时间）
    ↓
保护日志证据（不删除、不修改、不覆盖）
    ↓
脱敏后分析原因
    ↓
修复问题
    ↓
记录 Decision Log 或安全事件记录
    ↓
补充规则（为什么现有规则没防住？）
```

### 规则

1. **安全事件日志不得随意删除。** 删除日志 = 销毁证据。
2. **分析日志时必须脱敏。**
3. **涉及密钥必须立即更换。**
4. **涉及客户数据必须谨慎处理并评估是否需要通知。**
5. **安全事件必须复盘。**

## 27. 禁止事项

| # | 禁止事项 | 原因 |
|---|----------|------|
| 1 | 禁止日志记录 API Key | 密钥泄露 |
| 2 | 禁止日志记录 Token | 同上 |
| 3 | 禁止日志记录真实 `.env` | 同上 |
| 4 | 禁止日志记录 `DATABASE_URL` 完整值 | 数据库凭证泄露 |
| 5 | 禁止日志记录客户隐私数据 | 法律责任 + 职业道德 |
| 6 | 禁止日志记录 Authorization header | Token 在其中 |
| 7 | 禁止日志记录 Cookie | 会话劫持风险 |
| 8 | 禁止把真实日志提交 Git | Git 历史永久保留 |
| 9 | 禁止把敏感日志写入交付报告 | 报告可能被传播 |
| 10 | 禁止生产环境默认输出大量 DEBUG | 日志爆炸 + 性能影响 |

| 12 | 禁止删除审计日志 | 同上 |
| 13 | 禁止 Agent 日志记录敏感输入原文 | 客户数据保护 |
| 14 | 禁止 MCP 日志记录外部账号 Token | 凭证泄露 |
| 15 | 禁止为了省事关闭所有错误日志 | 放弃排查能力 |
| 16 | 禁止把复杂监控当成早期项目必需品 | 过度工程化 |

## 28. 当前阶段默认结论

1. **当前阶段不引入复杂监控平台。** 不装 Prometheus、Grafana、ELK。
2. **当前阶段优先建立日志规范和交付报告检查。** 规范先行。
3. **当前阶段真实日志默认不进入 Git。** `.gitignore` 已覆盖。
4. **当前阶段日志不得记录真实密钥。** 连开发日志也不行。
5. **当前阶段日志不得记录客户隐私。** 当前无客户数据，但提前约束。
6. **当前阶段 Agent 日志先记录摘要，不记录敏感原文。**
7. **当前阶段前端和后端错误必须能基本定位。** 不能"不知道哪里错了"。
8. **当前阶段交付报告必须说明是否有明显错误日志。** 有就写，没有也写"未发现"。
9. **当前阶段商业项目上线前再补充更完整的监控和告警。**
10. **Logging_Monitoring_Standard 必须先于正式产品开发完成。**
